# wallet-api

Сервис ведения кошельков — то, что раньше временно жило внутри
[google-auth](https://github.com/WalletTransactions/google-auth) (см. историю в README
[wallet-gateway](https://github.com/WalletTransactions/wallet-gateway)), теперь отдельный сервис со своей БД.

Полное описание HTTP API (пути, тела запросов/ответов, коды ошибок,
включая протокол `/sync/*`) — [`openapi.yaml`](openapi.yaml). Сервис отдаёт
его и сам: `GET /openapi.yaml` — файл как есть, `GET /docs` — Swagger UI
поверх него (вендоренный статический бандл, `third_party/swagger-ui/`, без
CDN — см. его README) с формой "Try it out" (кнопка Authorize принимает
`$ACCESS_TOKEN` из примера ниже).

```
браузер/клиент --(Authorization: Bearer / cookie session)--> wallet-api
                        проверяет подпись по JWKS auth-сервиса
                        (google-auth), сам никого не логинит
                            │
                            ▼
                  своя, отдельная база —
                  инстанс Postgres может быть тот же, что у
                  auth-сервиса, база — обязательно другая
```

## Что реализовано, а что нет

Сознательно залипуха без деталей — как и остальные сервисы проекта на этом
этапе, только на своей БД:

- **Есть:** `POST /sync/push`/`GET /sync/pull` — настоящий протокол синка
  Android-клиента (org/docs/TODO_mobile_sync.md, Фаза 2), см. "Синхронизация"
  ниже — счета, операции, валюты, иконки и т.д.
- **Есть:** `POST /sync/blobs`/`GET /sync/blobs/:sha256` — загрузка/выдача
  содержимого иконок (см. "Иконки — content-addressable blob" ниже).
- **Отчётов (`GET /api/reports/*`) здесь больше нет** — выделены в отдельный
  сервис [wallet-report](https://github.com/WalletTransactions/wallet-report), см. "Отчёты — выделены в
  отдельный сервис" ниже.
- **Есть:** `/api/ledger/*`, `/api/invites/accept` — доступ и приглашения
  (org/docs/TODO_mobile_sync.md, Фаза 6), см. "Доступ и приглашения" ниже.
- **Есть:** `/api/currency-pairs*` и `/api/currencies*` — курсы валют и
  свои валюты с веба, см. "Курсы валют" и "Валюты" ниже.
- **Есть:** `/api/admin/icons*` — общий набор иконок, ведёт администратор
  с веба, см. "Общие иконки" ниже.
- **Демо-REST кошельков (`POST`/`DELETE /api/wallets`) убран целиком**
  (2026-09-11) — им пользовался только временный demo-CRUD экран веб-
  фронтенда (wallet-web), настоящих данных кошелька он не нёс.
  Таблица `wallets` в схеме и её проверка в `Database::verify_schema()`
  остаются — это маркер первой миграции (000001), не про эту фичу.

## Своя БД

`DATABASE_URL` в `.env` этого сервиса указывает на **отдельную базу и
отдельную роль** от тех, что у auth-сервиса (там `users`/`refresh_tokens`,
здесь только `wallets`) — Postgres-**инстанс** (сервер) при этом может быть
тем же самым, это не принципиально. Важна именно роль, не только база — и
эта роль (как и auth-сервисная) сама по себе НЕ имеет прав DDL/`TRUNCATE`:
в проекте три Postgres-роли, не две (см. `infra/db/README.md`, "Три роли") —
отдельная роль-мигратор с правом DDL на обе базы, и по одной строго
DML-роли на каждый сервис. Раньше, до появления мигратора, auth-сервис
подключался буквально bootstrap-ролью образа `postgres` (фактически
суперпользователем) — если бы wallet-api использовал её же, просто к другой
базе, скомпрометированный wallet-api получал бы доступ и к
`users`/`refresh_tokens` тоже; разделение баз без разделения учёток
изоляцию только имитирует.

В `compose.yaml` так и сделано: один контейнер `db`, но три независимые
пары роль+база — `MIGRATOR_POSTGRES_*` (мигратор, никаким сервисом не
используется), `AUTH_POSTGRES_USER`/`AUTH_POSTGRES_DB` у auth-сервиса,
`WALLET_POSTGRES_USER`/`WALLET_POSTGRES_DB` у wallet-api. Всё заводится само
при первом старте `db` (см. `infra/db/init-db.sh` в корне репозитория — там же
`REVOKE CONNECT` на "чужую" базу с обеих сторон, defense in depth сверх
самого разделения ролей, и выдача только DML-прав каждой app-роли). При
запуске без Docker то же самое нужно накатить вручную ролью мигратора на
уже поднятый сервер — см. сам скрипт.

Отдельно от ролей — то, что это в принципе отдельная БД: у баз в Postgres
нет ни общих таблиц, ни FK/JOIN друг на друга. Отсюда следствие:
`wallets.owner_id` — **не** внешний ключ на какую-то локальную таблицу
пользователей, как было в google-auth — своей таблицы `users` здесь нет и
не будет. `owner_id` — это просто `sub` из уже проверенного access-токена
(см. ниже), доверяем ему как непрозрачному идентификатору; проверку, что
такой пользователь вообще существует, обеспечивает auth-сервис при выпуске
токена, а не эта БД.

**Таблицу сам сервис больше не создаёт.** Роль, которой он подключается
(`WALLET_POSTGRES_USER`), намеренно без прав DDL/`TRUNCATE` (см. `infra/db/README.md`
в корне репозитория, "Три роли") — схему накатывает отдельная роль-мигратор
версионированной миграцией, `infra/db/migrate.sh wallet up`
([golang-migrate](https://github.com/golang-migrate/migrate), см.
`wallet-api/migrations/` и `infra/db/README.md`, "Миграции") — отдельным шагом
ПОСЛЕ старта `db`, но ДО старта самого `wallet-api` (`init-db.sh` при первом
старте контейнера `db` заводит только роли/базы/права, схему — уже не он).
`db::Database::verify_schema()` (вызывается при старте) ничего не создаёт,
только проверяет, что таблица `wallets` уже есть, и падает с понятной
ошибкой, если нет (в т.ч. если миграции забыли накатить).

## Как проверяется токен (без своего OAuth)

wallet-api не логинит и не выпускает токены — эта часть целиком на
auth-сервисе (google-auth). Ровно тот же приём, что в
[wallet-gateway](https://github.com/WalletTransactions/wallet-gateway) (см. его README, "Как убрали общий
секрет") — а раньше и в wallet-bff, до того как SPA его упразднила (см.
README [wallet-web](https://github.com/WalletTransactions/wallet-web), "Куда делся wallet-bff"):

1. Читает токен — сначала заголовок `Authorization: Bearer`, иначе cookie
   `session` (см. `session.hpp`).
2. Проверяет подпись **публичным ключом** auth-сервиса (RS256) — забирает
   его с `GET {AUTH_SERVICE_URL}/.well-known/jwks.json` и кэширует в памяти
   (см. `util/jwks.hpp`).
3. Если подпись верна и токен не истёк — достаёт `sub`/`email`/`name`/`role`
   (и, если он там есть, `device_id`/`platform` — см. "Синхронизация" ниже)
   из payload.

Никакого общего секрета в `.env` — только `AUTH_SERVICE_URL`.

**Исправлено 2026-09-04:** до этого `session::current_user` на самом деле
читал ТОЛЬКО cookie — пункт 1 выше был написан верно, но не соответствовал
коду (`extract_bearer` попросту не существовал). Из-за этого мобильный
клиент (нет cookie jar, только заголовок) не смог бы пройти авторизацию
здесь вообще ни на одном эндпоинте — незаметно, пока эндпоинты
тестировались в основном через браузер/cookie; проявилось при появлении
`/sync/*`, которым Bearer нужен по определению.

## Доступ через гейтвей

Как и `/api/*` auth-сервиса раньше, эндпоинты этого сервиса теперь
проксирует [wallet-gateway](https://github.com/WalletTransactions/wallet-gateway) — см. его README и
`WALLET_API_URL` в его `.env`. Прямой поход в порт wallet-api (минуя гейтвей)
всё ещё работает для API-клиентов с `Authorization: Bearer` (curl, Postman) —
именно так и стоит его тестировать, cookie-флоу привязан к origin гейтвея.

## Пример

```bash
curl -X GET "http://127.0.0.1:8090/sync/pull?stream=reference&cursor=0" \
  -H "Authorization: Bearer $ACCESS_TOKEN"
# -> 200 {"changes":[...],"next_cursor":"..."}
```

(`$ACCESS_TOKEN` — тот же access-токен, что google-auth показывает на
success-странице после логина; см. его README. Полный протокол — см.
"Синхронизация" ниже и `openapi.yaml`/`GET /docs`.)

## Синхронизация (`POST /sync/push`, `GET /sync/pull`)

Протокол офлайн-first синка Android-клиента (org/docs/TODO_mobile_sync.md,
Фаза 2) — домен из `wallet-api/schema/table/` (`account`, `account_operating`,
`operation`, `operation_link`, `currency`, `currency_pair`,
`currency_pair_rate`, `currency_conversion`, `icon`), накатан миграцией
`wallet-api/migrations/000002_ledger_sync.up.sql`.

**Только для мобильного входа.** Оба эндпоинта требуют, чтобы токен нёс
claim `device_id` (см. README google-auth, "Детали устройства") — у токена
браузерного входа его нет, и без него провизионировать нечего (см. ниже).
Без него — `403`.

### Провизионирование — лениво, без отдельной регистрации

При первом обращении с новым `sub` сервис сам заводит (`src/provisioning.cpp`):
`app_user` (id = `sub`), персональный `ledger` с этим пользователем как
`owner` (MVP — один леджер на пользователя, шаринг на несколько человек не
реализован, план п. 1.3), и запись `device` (id = claim `device_id`).
Повторные вызовы просто обновляют `last_seen_at`/`email`/`platform`.

Устройство всегда записано на **текущий** леджер пользователя: после
принятия приглашения или удаления из участников `device.ledger_id`
переписывается при следующем `/sync/*`, а подтверждение потока леджера
(`last_ack_seq`) обнуляется — оно относилось к прежнему потоку (change
`purge-synced-tombstones`; этим закрыто наблюдение Р11 baseline —
`openspec/changes/archive/2026-10-26-baseline-wallet-api/design.md`, сам
архив не правится).

### `POST /sync/push`

```json
{
  "batch_id": "uuid",             // идемпотентность — см. ниже
  "device_name": "Pixel 7",       // опционально
  "changes": {
    "account": [ {"uuid": "...", "name": "Наличные", "comment": "", "icon_uuid": "...", "is_archived": false} ],
    "operation": [ {"uuid": "...", "date": "2026-01-15T10:00:00", "acc_fr_uuid": "...", "acc_to_uuid": "...", "amount": "500.00", "comment": ""} ]
  }
}
```

- `ledger_id`/`seq` клиент не присылает никогда — `ledger_id` сервер берёт
  из провизионирования (см. выше), `seq` — один вызов `next_seq()` на весь
  батч (см. `wallet-api/schema/README.md`, "Курсор и страницы").
- **`amount`/`rate` — строки**, не числа (см. `wallet-api/schema/README.md`,
  "Деньги — numeric") — так и передаются в SQL как есть, без разбора в
  double и обратно.
- Мягкое удаление — не отдельный метод, а поле `"deleted": true` в самой
  строке; сервер сам проставляет `deleted_at = now()` (не то, что мог бы
  прислать клиент — эта колонка только для диагностики).
- Вся `changes` — **одна транзакция** (`db::Database::Transaction`, см.
  `db.hpp`): либо применяется целиком, либо не применяется вовсе — важно для
  `operation_link` (обе ноги разновалютного перевода должны доехать вместе).
- **`icon` — обычная синхронизируемая таблица** (2026-09-05), но САМО
  содержимое (байты изображения) в push/pull не входит — см. "Иконки —
  content-addressable blob" ниже. Строка `icon`/`account`/`currency`,
  ссылающаяся на ещё не загруженный `content_sha256`/`icon_uuid`, получит
  `409 missing_reference` — тем же путём, что и любой другой внешний ключ.
- Дубль уникального индекса, отличного от `uq_account_name` (например,
  `icon.name` — см. `wallet-api/schema/table/icon.sql`), — **тоже не** роняет
  батч 500-й: `409 {"error":"duplicate_key","constraint":"<имя>"}`, но БЕЗ
  автоматического разрешения (нет `existing_uuid`, на который клиент мог бы
  переклеиться) — см. "Открытые вопросы" в `org/docs/TODO_mobile_sync.md`.
- Конфликт имени счёта (`uq_account_name`) — **не** абортит весь батч тихим
  500: `409 {"conflicts":[{"table":"account","reason":"duplicate_name","uuid":"...","existing_uuid":"..."}]}`
  (`uuid` — то, что прислал сам клиент в этой строке; без него клиенту нечем
  понять, какую из СВОИХ локальных строк переклеивать, если в одном батче
  конфликтует не один счёт). Клиент обязан переклеить операции на `existing_uuid` и повторить батч (см.
  `wallet-api/schema/table/README.md`, раздел `account`).
- Идемпотентность — `batch_id` (`sync_push_batch`): повторная отправка ТОГО
  ЖЕ `batch_id` возвращает сохранённый ответ, ничего не применяя заново. В
  кэш кладётся только успешный исход — конфликт пересчитывается заново на
  каждый повтор (дёшево и детерминированно, в отличие от успешного
  применения, которое нельзя тихо повторить без двойного расхода `seq`).
- Строка, не несущая обязательную для своей таблицы колонку
  (`TableSpec::columns`), — **`400 {"error":"invalid_row","detail":"..."}`**,
  не 500 и не необработанное исключение до глобального
  `svr.set_exception_handler`. Реальный случай (2026-09-09): `account`
  обзавёлся колонками `system_kind`/`kind`, а установленный на телефоне
  APK ещё их не отправлял — `row.at("system_kind")` в `sync_repo.cpp`
  бросал `json::out_of_range`, что раньше долетало как есть до
  `set_exception_handler` (`500 internal server error`, лог — "unhandled
  exception"). Транзакция батча откатывается целиком в обоих случаях (RAII
  `db::Database::Transaction`) — 400 просто называет причину внятно, вместо
  того чтобы полагаться на глобальный перехват.
- **Необязательные колонки push** (`TableSpec::optional_columns`, сегодня
  только `currency.show_in_equivalent`, миграция 000026). Строка без ключа
  такой колонки не ошибка: колонки нет ни в `INSERT` (работает `DEFAULT`
  таблицы — у флага `true`), ни в `DO UPDATE SET`, ни в `UPDATE` по uuid —
  у существующей строки прежнее значение остаётся. «Нет ключа» значит
  «клиент о колонке не знает». Ключ есть, но не boolean —
  `400 invalid_row`, `detail` называет поле. Почему не обязательная, как
  `account.kind`: у `kind` нет безопасного значения по умолчанию, а у флага
  есть (`true` — поведение до правки); обязательный флаг дал бы `400` на
  любой push с валютой с необновлённого телефона, и тот перестал бы
  синкаться совсем. Общая валюта push'ем по-прежнему не меняется.

### `GET /sync/pull?ledger_seq=&reference_seq=&ledger_id=&limit=`

```json
{
  "ledger": {"next_seq": 42, "changes": {"account": [...], "operation": [...]}},
  "reference": {"next_seq": 7, "changes": {"currency": [...], "currency_pair_rate": [...]}}
}
```

Два независимых курсора (см. `wallet-api/schema/README.md`, "Потоков два") —
`ledger` несёт данные леджера (включая СВОИ, не общие копии
валют/иконок/курсов), `reference` — только общие (`ledger_id IS NULL`).
`limit` — сколько строк добирать, но страница может выйти БОЛЬШЕ: группа
изменений с одинаковым `seq` (один push-батч) никогда не разрезается между
двумя вызовами (см. `wallet-api/schema/README.md`, "Курсор и страницы") — реализовано
одним SQL-запросом (`WITH candidates ... cutoff ...`, см. `sync_repo.cpp`),
не постраничной пересборкой в C++.

Курсор впереди головы потока — поток отдаётся с нуля, `reset: true`,
`reset_reason: "ahead"`; курсор отстал от чистки — `reset_reason: "purged"`
(см. ниже). Без сброса поля `reset_reason` нет.

### Срок хранения удалённых строк

Удалённые строки (`deleted_at`) нужны только затем, чтобы каждое устройство
узнало об удалении (`schema/README.md`, "Удаление — `deleted_at`"). Когда все
активные устройства их получили, сервер удаляет их физически (change
`purge-synced-tombstones`, миграция 000028):

- **Подтверждение.** Курсоры запроса `pull` записываются в
  `device.last_ack_seq` / `device.last_ack_reference_seq`: Android сохраняет
  курсор только после применения страницы, значит всё до него устройство
  уже применило. Пишется как есть, в том числе меньше прежнего; при сбросе
  — 0. Если передан `ledger_id` и он не совпадает с текущим леджером,
  подтверждение леджера не пишется (курсор от прежнего леджера).
- **Горизонт** потока — минимальное подтверждение среди устройств с
  подтверждением и `pull` не дольше `SYNC_TOMBSTONE_DEVICE_TTL_DAYS` (90)
  дней назад: для леджера — устройства этого леджера, для справочников —
  все. Нет таких устройств — голова потока. Бот (только `push`) и потерянный
  телефон чистку не держат.
- **Чистка** — после `pull`, не чаще раза в час на поток (атомарно через
  `change_stream.purged_at`), одной транзакцией: `DELETE` tombstone с
  `seq <= горизонт` по таблицам от листьев к корням, если на строку не
  ссылается ни одна строка синка (живая или удалённая) — таблица ссылок
  `sync_table_refs()` рядом с `pull_tables()` в `src/sync_repo.cpp`.
  `change_stream.purged_seq` поднимается до горизонта. Ошибка чистки
  пишется в лог (`sync_tombstone_purge_failed`), ответ `pull` не меняется.
- **Отставшее устройство** — курсор `0 < cursor < purged_seq`: поток с нуля,
  `reset_reason: "purged"`; клиент удаляет у себя строки потока, не
  пришедшие при перезагрузке (Android — свой change
  `purge-synced-tombstones`).
- **Загрузка с нуля — не отставание.** Устройство, начавшее поток с курсора 0
  (или после сброса), идёт по страницам, и граница страницы может быть ниже
  `purged_seq` (живые строки лежат в старых `seq`). Сервер запоминает
  `purged_seq` на момент старта (`device.ledger_load_base_seq` /
  `reference_load_base_seq`, миграция 000029) и, пока `purged_seq` не вырос,
  такой курсор не сбрасывает. Без этого загрузка в несколько страниц после
  первой чистки зацикливалась (ручная проверка на test, 2026-11-04). Вырасти
  мимо курсора активного устройства `purged_seq` не может — его
  подтверждение держит горизонт; вырос — устройство выпадало, сброс верен.

**Порядок включения.** `SYNC_TOMBSTONE_PURGE` по умолчанию `off`:
подтверждения и `reset_reason` работают сразу, строки не удаляются. `on` —
только когда телефоны обновились до Android-версии с вычисткой при старте с
нуля: старая версия на `purged` перезагрузит поток, но удалённые на сервере
строки останутся у неё «призраками». Откат — снова `off`; вычищенное не
вернуть, но его уже никто не ждал.

Строка `currency` в обоих потоках несёт булево `show_in_equivalent`
(миграция 000026): у общих валют его задаёт сервер, у своих — последний push
или `PATCH /api/currencies/:uuid`; валюты, созданные раньше, отдаются с
`true`.

### Иконки — content-addressable blob (`POST /sync/blobs`, `GET /sync/blobs/:sha256`)

Иконка требует и загрузки содержимого (байты изображения), и синка
метаданных (`name`/`icon_type`/ссылка на содержимое) — это НЕ одна операция:

1. **`POST /sync/blobs`** — тело запроса КАК ЕСТЬ (сырые байты, от 1 байта
   до 1 МиБ, см. `wallet-api/schema/table/blob.sql`), любой Content-Type не
   разбирается. Сервер сам считает SHA-256 (не доверяя тому, что мог бы
   прислать клиент), сохраняет `blob` (контент-адресуемый — одинаковое
   содержимое у разных пользователей хранится один раз, `ON CONFLICT DO
   NOTHING` делает повтор идемпотентным) и отвечает `{"sha256": "<64 hex>"}`.
2. Клиент включает строку `icon` в обычный `/sync/push` с полученным
   `content_sha256` (hex-строка, не сырые байты — см. `TableSpec::
   hex_columns`) — как любую другую синхронизируемую таблицу. Если blob ещё
   не залит — `409 missing_reference` (внешний ключ
   `icon.content_sha256 → blob.sha256`), тем же путём, что и любая другая
   ссылка.
3. **`GET /sync/blobs/:sha256`** — отдаёт сырые байты (`application/
   octet-stream`) для устройства, которому нужно содержимое иконки, чей
   `uuid`/`content_sha256` оно уже получило через `/sync/pull`, но байтов
   которой у него ещё нет.

Оба эндпоинта требуют только обычную сессионную аутентификацию
(`session::current_user`), **не** `device_id` — blob "ничей" (нет
`ledger_id`, см. `wallet-api/schema/table/blob.sql`, "Строки намеренно ничьи"),
браузерный вход тут годится не хуже мобильного. Право прочитать КОНКРЕТНЫЙ
blob по видимости соответствующей иконки в леджере вызывающего в этом
заходе **не проверяется** — только факт аутентификации (см. открытый вопрос
в `org/docs/TODO_mobile_sync.md`).

Полный контракт (коды ответов, форма ошибок) — `openapi.yaml`.

## Доступ и приглашения (`/api/ledger/*`, `/api/invites/accept`)

org/docs/TODO_mobile_sync.md, Фаза 6. `ledger_id` нигде не принимается от
клиента (тот же принцип, что у `/sync/*`) — резолвится из леджера ТЕКУЩЕГО
пользователя (`invites_repo::find_membership`), поэтому в путях нет
`{ledger_id}`, только `/api/ledger/...` (MVP — один леджер на пользователя).

- **`GET /api/ledger/members`** — участников видят все роли; управляющие
  ручки ниже — только `owner` (проверяется на каждый запрос сервером, не
  только скрытием кнопок на фронте).
- **`PATCH`/`DELETE /api/ledger/members/:user_id`** — сменить роль
  (`member`/`reader`, не `owner`) или удалить участника. Владельца нельзя ни
  переключить, ни удалить этим путём — `invites_repo::set_member_role`/
  `remove_member` фильтруют `role <> 'owner'` в самом `WHERE`, для строки
  владельца оба возвращают "не найдено" (404), не отдельную диагностику.
- **`POST /api/ledger/transfer-owner`** — передача владения. Одна транзакция,
  **два последовательных `UPDATE`, не один `CASE`**
  (`invites_repo::transfer_owner`): `uq_ledger_member_owner` — частичный
  уникальный ИНДЕКС, а не `DEFERRABLE CONSTRAINT` (частичный индекс не может
  быть основой отложенного ограничения в Postgres), поэтому уникальность
  проверяется по каждой строке немедленно — один `UPDATE`, выставляющий
  `owner` двум строкам сразу через `CASE`, рискует временным дублем в
  зависимости от порядка обработки строк движком.
- **`POST`/`GET /api/ledger/invites`, `DELETE /api/ledger/invites/:id`** —
  выпустить/посмотреть активные/отозвать одноразовую ссылку. Токен —
  32 случайных байта (`crypto::random_bytes`, OpenSSL `RAND_bytes`), в БД
  хранится только его `sha256` (`ledger_invite.token_hash`) — тем же
  приёмом, что `google-auth` хранит refresh/access-токены. Сырой токен
  отдаётся ТОЛЬКО в ответе на `POST` — `GET` (список активных) его не
  возвращает вообще, показать ссылку повторно нельзя. **Поля `link` в ответе
  нет** — только `token`: собрать ссылку (`location.origin + '/join/' +
  token`) должен сам вызывающий клиент, wallet-api в LAN-only MVP не знает
  публичный адрес wallet-web (тот же принцип, что `resolve_redirect_uri` в
  `google-auth`, — сервер не хардкодит и не угадывает чужой публичный хост).
- **`POST /api/invites/accept`** — принять по токену. Одноразово —
  `UPDATE ledger_invite ... WHERE used_at IS NULL AND revoked_at IS NULL AND
  expires_at > now()`, вторая попытка тем же токеном находит 0 строк (`410`).
  MVP держит инвариант "один леджер на пользователя" (см. `servers/
  TODO_mobile_sync.md`, п. 1.3) — если у принимающего уже есть леджер,
  `409`, и приглашение **не расходуется** (годится следующему).
  В ответе `409` есть `ledger_empty`: `true`, если вызывающий в своём
  леджере один и туда ни разу ничего не записывалось (`change_stream.seq =
  0`). Тогда повтор с `replace_empty_ledger: true` удаляет пустой леджер и
  принимает приглашение одной транзакцией. `seq = 0` нужен не только как
  признак пустоты: курсор леджерного потока на устройствах пользователя
  тоже 0, и после переезда pull нового леджера ничего не пропустит.
  Непустой леджер этим путём не удаляется никогда.

Полный контракт — `openapi.yaml`, тег `ledger`.

## Удаление аккаунта (`DELETE /api/account`)

Самообслуживание — "Удалить аккаунт" в настройках wallet-web (по прямому
запросу, 2026-09-14: "удаление счета... при согласии удаление всей учетки
из валлет И аус сервиса"). Жёсткое (не мягкое/анонимизация) удаление ВСЕХ
данных вызывающего пользователя в этой базе, одной транзакцией
(`account_deletion_repo::delete_own_account`, файл намеренно НЕ
`account_repo` — в схеме уже есть таблица `account`, кошельки/категории, это
про совсем другое):

1. Леджеры, где вызывающий — единственный участник (`role='owner'`, никого
   больше в `ledger_member`), удаляются целиком: `DELETE FROM ledger`
   каскадом (`ON DELETE CASCADE`, см. `wallet-api/schema/table/*.sql`) сносит
   `ledger_member`/`ledger_invite`/`device`/`account`/`account_operating`/
   `operation`/`operation_link`/`sync_push_batch`/`currency`/
   `currency_pair`/`currency_pair_rate` этого леджера — один каскад, не
   десяток ручных `DELETE` в правильном порядке. Следом — `DELETE FROM
   change_stream` (`ledger.id REFERENCES change_stream ON DELETE RESTRICT` —
   поток обязан пережить сам леджер ровно настолько, чтобы не остаться
   осиротевшим).
2. `DELETE FROM app_user` — каскадом снимает членство ЭТОГО пользователя в
   ЧУЖИХ леджерах (он там просто участник — это и есть "выйти из общего
   кошелька", не удаляя сам леджер и данные остальных), любые оставшиеся
   `device` и `ledger_invite` (`created_by`/`used_by`).

**Если пользователь — владелец леджера, где есть ДРУГИЕ участники** —
`409`, ничего не трогается: жёсткое удаление снесло бы данные, которыми
пользуются они. Сначала `POST /api/ledger/transfer-owner` или `DELETE
/api/ledger/members/{user_id}` (обе ручки — см. "Доступ и приглашения"
выше). На MVP ("один леджер на пользователя, свой, без иных участников",
`provisioning.cpp::ensure_personal_ledger`) этот путь не встречается —
защита на будущее, когда шаринг (Фаза 6) станет обычным делом.

Идемпотентно — вызов для `user_id`, у которого и так уже нет ни `app_user`,
ни `ledger_member` (никогда не провизионировался, либо уже был удалён
раньше), просто ничего не находит и возвращает `204`, не ошибку.

**Не удаляет саму идентичность** — это отдельный, независимый вызов
`DELETE /auth/me` в google-auth (своя база, свои токены в Redis, см. её
README). Два разных сервиса, общей транзакции нет — wallet-web (настройки,
"Удалить аккаунт") вызывает СНАЧАЛА этот эндпоинт, ПОТОМ `DELETE /auth/me`:
обрыв между ними оставляет пользователя без данных, но ещё способным войти
и повторить (безопасно — см. идемпотентность выше), а не идентичность без
данных, которой она принадлежит.

Проверено интеграционными тестами против живого Postgres
(`tests_integration/test_account_deletion.cpp`): единственный владелец —
всё сносится (включая настоящую строку `account`, не только служебные
таблицы); владелец с другим участником — отказ, ничего не тронуто; просто
участник — выходит из чужого леджера, не трогая его; никогда не
провизионировался — idempotent `204`. Полный контракт — `openapi.yaml`, тег
`account`.

## Курсы валют (`/api/currency-pairs*`)

По прямому запросу пользователя — веб-аналог Android-экранов
`CurrencyPairListActivity`/`CurrencyPairRateListActivity`/`RateEditDialog`:
просмотр валютных пар и истории их курса, добавление/изменение/удаление
пары и её курса. Реализация — `src/currency_pairs_repo.hpp/.cpp` (логика,
без httplib — тот же приём, что `sync_repo`/`invites_repo`) + `src/
currency_pairs.hpp/.cpp` (тонкий HTTP-слой, обычная сессионная
аутентификация без `device_id`, тем же принципом, что `invites.hpp`).

**Область видимости — та же `Scope::ReferenceOrLedger`, что у справочников
синка** (`currency_pair`/`currency_pair_rate`, `ledger_id IS NULL` = общее,
видно всем; заполнено = личная копия леджера, см. `wallet-api/schema/README.md`).
Веб всегда СОЗДАЁТ личные строки (`create_pair` всегда пишет аутентифи­
цированный `ledger_id`, никогда `NULL`) — тот же принцип, что у мобильного
push (`org/docs/TODO_mobile_sync.md`, Фаза 2, п. 5, "клиент физически не
может создать общую строку"). Править/удалять можно ТОЛЬКО свои строки —
общие видны в списке (`is_own: false`), но `PATCH`/`DELETE` на них отвечают
тем же `404`, что и несуществующий uuid (неотличимо намеренно — леджер не
должен даже узнать, что uuid вообще существует, но принадлежит не ему).
Курс — исключение из этого правила: `POST .../rates` можно ставить и на
ОБЩУЮ пару — заводит ЛИЧНЫЙ курс, сосуществующий с общим на ту же дату (та
же семантика, что уже действует у `currency_pair_rate` для мобильного
push, см. `uq_currency_pair_rate_ledger`), саму пару это не трогает.

**Роль участника леджера (`owner`/`member`/`reader`) НЕ проверяется** — тот
же принцип, что и у `/sync/push` (там роль вообще не смотрится ни для одной
таблицы, см. `provisioning.cpp`): вводить проверку роли только здесь
рассинхронизировало бы политику с остальными путями записи этого сервиса.

**`seq`/`change_stream`** — каждая мутация (создание пары, правка
`precision`, мягкое удаление пары + каскад её курсов, апсерт/удаление
курса) — одна транзакция с ОДНИМ `next_seq()` на все её строки, тот же
протокол версий, что у `/sync/push`: мобильные устройства получат эти
изменения обычным `GET /sync/pull`, для этого протокола правки с веба
неотличимы от правок с телефона. `updated_by` (устройство) не проставляется
(остаётся `NULL`) — у веб-сессии нет `device_id`, колонка и так nullable,
это только диагностика.

**Найден и исправлен реальный дедлок (2026-09-10, интеграционным тестом)** —
тот же класс бага, что уже был в `push_batch` (`sync_repo.cpp`, 2026-09-04):
`create_pair`/`update_pair_precision` коммитили свою `db::Database::
Transaction` и СРАЗУ после звали `find_pair()` (обычный `db.exec()`) — но
`Transaction` держит `mutex_` соединения ВСЁ время своей жизни, не только до
`commit()` (см. `db.hpp`), а сама переменная `tx` была ещё жива (не вышла из
области видимости) на этой строке. Второй запрос ждал тот же неповторно
входимый `mutex_`, который держал первый — самозаклин навсегда. Исправлено
сужением области видимости `tx` до фигурных скобок, заканчивающихся сразу
после `commit()` — `find_pair()` вызывается уже ПОСЛЕ разрушения `tx`.
**Не поймать было ни код-ревью, ни компиляцией** — только интеграционным
тестом до конца (тот же урок, что и в 2026-09-04): `create_pair_then_list_
pairs_shows_it_as_own` зависал молча (0% CPU, `pg_stat_activity` показывал
сессию `idle`, `wait_event: ClientRead` после `COMMIT` — Postgres давно
ответил, клиент просто не отправил следующий запрос).

- **`GET /api/currency-pairs`** — видимые пары (своя перекрывает общую с тем
  же символом, `DISTINCT ON (symbol)`), у пользователя ещё нет леджера —
  `200` с пустым списком, не `404` (тот же принцип, что у отчётов).
- **`POST /api/currency-pairs`** — **единственная ручка этого раздела,
  заводящая леджер** при первом обращении (`provisioning::
  ensure_personal_ledger`, тот же лениво-создаваемый персональный леджер,
  что и в `ensure_identity`, только без записи в `device` — у веб-сессии
  его нет). Символ (`"EURUSD"`) строится сервером из ISO-кодов валют, не
  принимается от клиента. Валюты обязаны быть ВИДИМЫ этому пользователю
  (своя или общая) — иначе `400`, не `500` на чужом внешнем ключе: леджер Б
  не должен даже узнать о существовании приватной валюты леджера А через
  код ошибки.
- **`PATCH`/`DELETE /api/currency-pairs/:uuid`** — изменить точность/удалить
  СВОЮ пару. `DELETE` каскадно мягко удаляет и все ещё живые курсы этой пары
  — тем же `seq`, что и сама пара (одна атомарная группа).
- **`GET .../rates`** — история курса (`from`/`to`, `YYYY-MM-DD`,
  включительно, необязательны), своя строка перекрывает общую на ту же
  дату — тот же приоритет, что у списка пар.
- **`POST .../rates`** — апсерт своего курса по естественному ключу
  (леджер, пара, дата) — второй вызов на ту же дату ОБНОВЛЯЕТ строку
  (сохраняя её `uuid`), не плодит вторую (тот же принцип, что
  `WalletDbCRUD.InsertOrReplaceRate` на Android-клиенте).
- **`DELETE .../rates/:date`** — удалить СВОЙ курс на дату. Если своей
  строки нет (есть только общий курс) — `404`: общий курс этим путём не
  удаляется.

**Сознательно не перенесено с Android**: загрузка исторических курсов из
внешних источников (Yahoo Finance/Frankfurter/ЦБ РФ,
`CurrencyPairRateListActivity.downloadRates`) — отдельная, более крупная
задача (сетевые интеграции с тремя разными форматами ответа), не входящая
в прямой запрос "добавление/удаление/изменение пары и её курса".

Полный контракт — `openapi.yaml`, тег `currency-pairs`.

## Валюты (`/api/currencies*`)

Свои валюты леджера с веба (change `currency-ui-tweaks`): `POST
/api/currencies`, `PATCH`/`DELETE /api/currencies/:uuid`. Копия устройства
«Курсов валют» выше: логика — `src/currencies_repo.hpp/.cpp`, HTTP-слой —
`src/currencies.hpp/.cpp`, scope `wallet:read` на GET/HEAD и `wallet:write`
на остальное (`access.cpp`; префикс `/api/currency-pairs` этот путь не
покрывает — строки расходятся после `currenc`). Чтения справочника здесь
нет — это `GET /api/reports/currencies` в wallet-report. Ответ `POST`/`PATCH`
— та же форма строки, что элемент того справочника (`uuid`, `name`,
`iso_code`, `symbol`, `precision`, `icon_uuid`, `icon_sha256`,
`show_in_equivalent`, `is_own`), веб подставляет её без перезапроса.

- **Создание** — обязательны `name`, `iso_code`, `icon_uuid` (общая иконка
  или иконка своего леджера, иначе `400`). `iso_code` → верхний регистр,
  края `name`/`symbol` обрезаются, пустой `symbol` = `iso_code`,
  `precision` 0–8 (`CHECK` таблицы, не 0–10, как у пар), по умолчанию 2,
  `show_in_equivalent` по умолчанию `true`. Леджер при необходимости
  создаётся (`ensure_personal_ledger`). `400` несёт `field`.
- **Уникальность** — код (после приведения регистра) и название сверяются
  со **всеми** видимыми живыми валютами, своими и общими (как
  `getCurrencyByISO` на телефоне): индексы `uq_currency_*_ledger` общую
  валюту не видят, поэтому проверка явная. `409
  {"error":"duplicate","field":"iso_code"|"name"}`; гонка на индексе
  отображается в тот же `409`.
- **Код валюты пары не меняется** — `PATCH` с другим `iso_code` у валюты,
  входящей в живую пару (базой или котируемой), — `409 currency_in_pair`:
  символ пары — склейка кодов, и пересчитывать его пришлось бы и на
  телефоне. Остальные поля такой валюты правятся.
- **Удаление** — мягкое; живой кошелёк в этой валюте или живая пара с ней —
  `409 currency_in_use` (правило `IsCurrencyInUse` телефона).
- **Общие валюты** этим API не меняются — `404`, как чужие и удалённые.
  Скрыть общую валюту из эквивалента для одного леджера нельзя, а своя с
  тем же кодом запрещена правилом уникальности — принято (design D1).
- Каждое изменение — одна транзакция с одним `next_seq(ledger)`,
  `updated_by = NULL`, роль участника не проверяется — как у пар. На
  телефоны доходит обычным `GET /sync/pull`.

Полный контракт — `openapi.yaml`, тег `currencies`.

## Общие иконки (`/api/admin/icons*`, только администратор)

Общий набор иконок (`icon.ledger_id IS NULL`, едет всем) ведёт
администратор с веба (change `server-managed-icons`); телефон эти иконки
только скачивает. Логика — `src/reference_icons_repo.hpp/.cpp`, HTTP-слой —
`src/reference_icons.hpp/.cpp`. Это первые ручки wallet-api, которые
смотрят claim `role`: scope `wallet:write` при любом методе проверяет гейт
(`access.cpp`, раньше роли), затем хендлер требует `role = admin` — иначе
`403 {"error":"forbidden"}` (claim'а нет — то же самое). `device_id` не
нужен, леджер и устройство не провизионируются. Путь — `/api/admin/*`, его
гейтвей ведёт сюда общим правилом `/api/*` (не путать с `/admin/*` —
google-auth). Чтение набора — `GET /api/reports/admin/icons` в wallet-report.

- **Создание — в два шага.** Сначала байты картинки: `POST /sync/blobs`
  (см. «Иконки — content-addressable blob» выше; лимит 1 МиБ, сервер сам
  считает SHA-256), затем `POST /api/admin/icons` с `name` (края
  обрезаются, 1–64 символа), `icon_type` (целое ≥ 0; 1 — флаг, остальное —
  категория) и `content_sha256` из ответа загрузки. Хеш без загруженного
  содержимого — `400` с `field` = `content_sha256`; живая общая иконка с
  тем же именем — `409 {"error":"duplicate","field":"name"}`. Ответ `201` —
  `uuid` (выдаёт сервер), `name`, `icon_type`, `content_sha256`. Формат
  картинки сервер не проверяет — веб приводит её к WEBP 256×256 до загрузки.
- **Правка** — `PATCH /api/admin/icons/:uuid` с `name` и/или `icon_type`.
  Картинку существующей иконки не меняем (телефон не перекачивает байты
  известной иконки): `content_sha256` в теле — `400`, для новой картинки
  создаётся новая иконка. Своя иконка леджера, удалённая или неизвестная —
  `404`.
- **Удаление — только неиспользуемой.** `DELETE /api/admin/icons/:uuid`
  мягко удаляет иконку (`204`), если на неё не ссылается ни один живой
  `account` или `currency` любого леджера; иначе `409
  {"error":"in_use","in_use":N}`. Причина: по tombstone иконки новое
  устройство пропустило бы при pull ссылающиеся на неё счета. `blob` не
  удаляется (сборка мусора — отдельная задача).
- Каждое изменение — одна транзакция с одним `next_seq` потока справочников
  (`00000000-0000-0000-0000-000000000001`), `updated_by = NULL`. На все
  устройства доходит обычным `GET /sync/pull` (раздел `reference`,
  `changes.icon`; удаление — tombstone с `deleted_at`). Протокол синка не
  меняется: `POST /sync/push` по-прежнему принимает строки `icon` от старых
  версий приложения.

Полный контракт — `openapi.yaml`, тег `admin-icons`
(`createReferenceIcon`/`updateReferenceIcon`/`deleteReferenceIcon`).

## Версия

`GET /version`, строка лога при старте и `build_info` в `GET /metrics` —
общая схема для всех 4 C++-сервисов проекта, см. README google-auth,
"Версия" (файл `VERSION` + git-хэш, откуда берутся, как проставляются на
билде — код и приём идентичны). Там же — `build` (тег образа из
`--build-arg APP_BUILD`) и `started_at` (время запуска) в `GET /version`.

Релиз — git-тегами: `vX.Y.Z-rc.N` публикует образ в ghcr и выкатывает его
в test, `vX.Y.Z` на том же коммите — тот же образ в prod; `X.Y.Z` должен
совпадать с `VERSION`. Подробно — [README google-auth, «Версия»](https://github.com/WalletTransactions/google-auth#версия), «Релиз».

## Логирование

Общая схема для всех сервисов проекта (см. README google-auth, раздел
"Логирование" — тут то же самое, код `src/util/log.*` идентичен): JSON-строка
на запись (`ts`/`level`/`service`/`trace_id`?/`msg`, `ts` — всегда UTC), папка
`LOG_DIR` (по умолчанию `logs/` на Windows, stdout на Linux/в Docker), внутри
— файл на каждый календарный день с именем сервиса
(`2026-08-25-wallet-api.log`), ротация по смене даты, старые файлы не
трогаются. `trace_id` — сквозной id запроса браузера через gateway → этот
сервис (см. README google-auth, "Логирование").

Каждый SQL-запрос (`db::Database::exec()`, см. `src/db.cpp`) логируется
отдельной строкой с `sql`/`duration_ms`/`rows` (латенси именно похода в
Postgres) — см. README google-auth, "Логирование", там же про
`LOG_SQL_PARAMS`, если нужно видеть ещё и значения параметров запроса, и про
`LOG_SQL_MASK_PARAMS` — какие из этих значений маскируются "***" независимо
от `LOG_SQL_PARAMS`.

## Конфигурация

```bash
cp .env.example .env
```

- `AUTH_SERVICE_URL` — адрес auth-сервиса (google-auth), откуда тянутся
  публичные ключи для проверки токена.
- `DATABASE_URL` — строка подключения к СВОЕЙ базе под СВОЕЙ ролью (см. "Своя
  БД" выше) — ни база, ни логин/пароль не должны совпадать с тем, что в
  `DATABASE_URL` google-auth; инстанс Postgres при этом может быть общим.
  (`REPORTS_DATABASE_URL`/роль `wallet_reader` этому сервису больше не
  нужны — см. README [wallet-report](https://github.com/WalletTransactions/wallet-report).)
- `DATABASE_POOL_SIZE` — сколько соединений с этой ролью держать одновременно
  (по умолчанию `8`, см. `src/db.hpp::Pool`) — раньше сервис держал ровно
  одно на весь процесс, и один медленный запрос (крупный `push`, конфликт с
  ретраем) блокировал вообще все остальные на всё время своего выполнения.
- `PORT` — по умолчанию `8082` (у google-auth занят `8080`, у wallet-web —
  `8083`, у гейтвея — `8090`).
- `SYNC_TOMBSTONE_PURGE` — `on`, чтобы физически чистить удалённые строки
  синка (по умолчанию `off`); см. "Срок хранения удалённых строк" — порядок
  включения. `SYNC_TOMBSTONE_DEVICE_TTL_DAYS` — через сколько дней без `pull`
  устройство перестаёт держать чистку (по умолчанию `90`). Оба значения —
  в стартовом логе (`sync_tombstone_config`).
- `LOG_SQL_PARAMS` — `true`/`1`, чтобы писать в лог ещё и значения параметров
  SQL-запросов ($1, $2, ...), не только сам текст запроса; по умолчанию
  выключено (см. "Логирование" выше, почему).
- `LOG_SQL_MASK_PARAMS` — доп. имена параметров через запятую, чьи значения
  `exec()` маскирует `"***"` в логе при `LOG_SQL_PARAMS=true` — расширяет
  встроенный набор (`password`, `client_secret`, `refresh_token`,
  `access_token`, `id_token`, `token`, `secret`, см.
  `builtin_mask_param_names()` в `src/db.cpp`), а не заменяет его; сейчас в
  этом сервисе секретов среди параметров запросов нет (см. "Своя БД" выше),
  переменная — задел на будущее.

## Сборка и запуск

```bash
cmake -B build
cmake --build build --config Release
build/Release/wallet_api.exe   # Windows; на Linux — build/wallet_api
```

Или `scripts/windows/run-console.bat` / `install-service.bat` (NSSM) — те же
скрипты, что у остальных сервисов, см. README google-auth за подробностями
по NSSM/systemd, здесь просто переименовано под `wallet_api`.

Перед первым запуском убедитесь, что google-auth уже поднят на
`AUTH_SERVICE_URL` — wallet-api сам по себе никого не логинит, только
проверяет уже выданные токены.
