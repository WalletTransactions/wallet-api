# Роли базы

Права выдаются ролям, а не схемам PostgreSQL — так было заложено ещё в прототипе
сервиса отчётов на Python (удалён 2026-09-30; логика переезжает в C++, см.
[`../../../wallet-infra/README.md`](https://github.com/WalletTransactions/wallet-infra/blob/main/README.md)).

| Файл | Роль | Права |
| --- | --- | --- |
| [`wallet_reader.sql`](wallet_reader.sql) | `wallet_reader` | `SELECT` на все таблицы и представления, `EXECUTE` на три отчётные функции. Ни одной привилегии записи |

Остальные роли, задуманные в прототипе (`wallet_migrate`, `wallet_api`,
`wallet_auth`, `wallet_rates`) появятся здесь вместе со своими сервисами: выдавать
права на запись раньше, чем есть кому писать, — значит держать в базе роль,
которой никто не пользуется, и про которую забудут при первом инциденте.

## Правила

**Файл роли обязан быть идемпотентным и лечащим.** `apply.sql` прогоняют по
существующей базе, и файл должен приводить роль к описанному в нём состоянию, а
не падать на «роль уже есть» и не оставлять руками выданные привилегии. Отсюда
`DO`-блок вместо `CREATE ROLE`, отдельный `ALTER ROLE` для атрибутов и явный
`REVOKE` на права записи.

**Гранты идут после DDL.** `GRANT ... ON ALL TABLES IN SCHEMA` разворачивается в
список таблиц в момент выполнения, поэтому включение роли стоит в `apply.sql`
последним. Для таблиц, которые появятся позже, есть `ALTER DEFAULT PRIVILEGES` —
но он действует только на объекты, созданные той же ролью, что применяла схему.

**Пароль в файле — только для локальной разработки.** На стенде с настоящими данными пароль задаётся вне
репозитория (`ALTER ROLE ... PASSWORD`), а сервис берёт DSN из окружения.
