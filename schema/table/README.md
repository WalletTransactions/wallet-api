# Таблицы

Построчная справка. Общие решения — почему `uuid` вместо автоинкремента, почему
`seq` вместо времени, почему `deleted_at` вместо `DELETE` — разобраны в
[`../README.md`](../README.md), здесь только то, что специфично для таблицы.

## Общий набор колонок синхронизируемой таблицы

Есть у `icon`, `currency`, `currency_pair`, `currency_pair_rate`,
`currency_conversion`, `account`, `account_operating`, `operation`,
`operation_link` — и ни у одной из служебных.

| Поле | Тип | Описание |
| --- | --- | --- |
| `uuid` | uuid NOT NULL | Идентичность строки. **Генерирует клиент** при создании записи, в том числе офлайн |
| `ledger_id` | uuid | Владелец. `NOT NULL` в таблицах данных леджера; в справочных допускает `NULL` — это общая строка, которая едет всем |
| `seq` | bigint NOT NULL | Версия строки в своём потоке изменений. Выдаёт [`next_seq()`](../function/next_seq.sql), одно значение на батч |
| `deleted_at` | timestamptz | Tombstone. Заполнено — строка удалена, но физически на месте |
| `updated_at` | timestamptz NOT NULL | Только диагностика; порядок задаёт `seq`. Проставляет триггер `set_updated_at` |
| `updated_by` | uuid → `device.id` | Какое устройство записало последним. `ON DELETE SET NULL`: снятие устройства не должно уносить данные |

Первичный ключ различается по области видимости:

- **таблицы данных леджера** (`account`, `account_operating`, `operation`,
  `operation_link`) — составной `(ledger_id, uuid)`. Он же цель составных внешних
  ключей, он же условие для будущего секционирования по `ledger_id`: PostgreSQL
  требует, чтобы ключ секционирования входил в каждое уникальное ограничение, и
  одиночный `uuid` закрыл бы эту дверь навсегда. Плата — `uuid` уникален в
  пределах леджера, а не глобально; протоколу этого достаточно, строка всегда
  адресуется вместе со своим леджером;
- **справочные таблицы** — одиночный `uuid`: их `ledger_id` допускает `NULL`, а
  колонка первичного ключа обязана быть `NOT NULL`. Секционировать их по леджеру
  всё равно незачем.

Индексы лент изменений устроены одинаково: в таблицах леджера один
`(ledger_id, seq)`, в справочных два частичных — `(seq)` для общей области и
`(ledger_id, seq)` для личной.

# Служебные таблицы

## `change_stream`

Счётчики версий. Строка на каждый леджер (`kind = 'ledger'`) плюс одна на всю базу
для общих справочников (`kind = 'reference'`, фиксированный id
`00000000-0000-0000-0000-000000000001`).

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | uuid PK | Для потока леджера совпадает с `ledger.id` |
| `kind` | text, CHECK | `'ledger'` \| `'reference'` |
| `seq` | bigint NOT NULL DEFAULT 0 | Текущее значение счётчика |

Поток леджера и сам леджер — одна сущность, разнесённая по двум таблицам с общим
первичным ключом. Это тот же приём, что `account_operating` над `account` в
клиентской схеме. Следствие для кода: создание леджера — всегда две вставки в
одной транзакции, сначала в `change_stream`.

## `ledger`

Единица владения и единица синхронизации: всё, что пользователь видит в
приложении, принадлежит ровно одному леджеру.

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | uuid PK → `change_stream.id` | `ON DELETE RESTRICT` — поток не должен остаться осиротевшим |
| `name` | text NOT NULL | |
| `created_at` | timestamptz NOT NULL | |

## `app_user`

**С 2026-09-04 проще, чем ниже предполагалось.** `id` — НЕ
`gen_random_uuid()`, а claim `sub` уже проверенного access-JWT (внутренний
`UserRecord.id` google-auth) — третий слой идентичности поверх него
(отдельный `google_sub`/свой uuid) оказался лишним: wallet-api и так уже
доверяет `sub` как непрозрачному идентификатору, тем же приёмом, что раньше
демо-таблица `wallets.owner_id`.

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | uuid PK | Claim `sub` уже проверенного access-JWT — не порождается этой базой |
| `email` | text | Кэш claim `email` из JWT, только для показа/поддержки. В решениях о доступе не участвует |
| `created_at` | timestamptz NOT NULL | |
| `disabled_at` | timestamptz | Зарезервировано, пока ничего не выставляет |

## `ledger_member`

Кто имеет доступ к леджеру и с какими правами. PK `(ledger_id, user_id)`.

| Поле | Тип | Описание |
| --- | --- | --- |
| `role` | text, CHECK | `'owner'` \| `'member'` \| `'reader'` |
| `joined_at` | timestamptz NOT NULL | |

`uq_ledger_member_owner` — частичный уникальный индекс по `ledger_id` при
`role = 'owner'`: владелец ровно один, потому что «два владельца» не имеет разумной
семантики при конфликте. Передача владения — `UPDATE` двух строк в одной транзакции.

## `ledger_invite`

Одноразовая пригласительная ссылка — второй, явный путь получить строку в
`ledger_member` (org/docs/TODO_mobile_sync.md, Фаза 6), кроме ленивого
provisioning при первом входе.

| Поле | Тип | Описание |
| --- | --- | --- |
| `ledger_id` | uuid NOT NULL | Леджер, в который приглашают |
| `role` | text, CHECK | `'member'` \| `'reader'` — **не** `'owner'` |
| `token_hash` | text NOT NULL, UNIQUE | `sha256(сырой токен)` hex — сырой токен в БД не хранится вовсе |
| `created_by` | uuid NOT NULL | Кто выпустил |
| `expires_at` | timestamptz NOT NULL | Срок (2/7/30 дней при создании) |
| `revoked_at` | timestamptz | Отозвана вручную |
| `used_at` / `used_by` | timestamptz / uuid | Заполняются вместе, ровно один раз — вторая попытка `accept` находит 0 строк |

"Активно" не хранится отдельным полем — `revoked_at IS NULL AND used_at IS
NULL AND expires_at > now()`, тот же приём, что `deleted_at` у `account`/
`operation`. Токен хэшируется тем же способом, что `google-auth` хранит
refresh/access-токены.

## `device`

**С 2026-09-04 проще, чем ниже предполагалось.** Это книга устройств для
курсоров синка и диагностики, **не** точка выдачи/ротации refresh-токенов —
вся выдача, ротация и отзыв токенов централизована в google-auth (Redis, см.
его README «Детали устройства»); wallet-api токены не выпускает и не
ротирует вообще, только проверяет уже готовый JWT по JWKS. Полей
`refresh_hash`/`refresh_family`/`refresh_expires_at`/`refresh_prev_hash`/
`refresh_prev_until`/`revoked_at` здесь больше нет — параллельная
инфраструктура ротации, которой ничто не пользуется, была бы декорацией.

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | uuid PK | Claim `device_id` уже проверенного access-JWT (генерирует Android при первой установке) — не порождается этой базой |
| `user_id`, `ledger_id` | uuid NOT NULL | |
| `name`, `platform` | text NOT NULL DEFAULT `''` | Из тела запроса мобильного входа (google-auth, `POST /auth/google/mobile`), только для показа человеку; `platform` заодно claim токена. CHECK по `android`/`ios`/`web`/`other`/`''` |
| `last_seen_at` | timestamptz | |
| `last_ack_seq` | bigint | Справочная копия курсора клиента — для диагностики и «сбросить синхронизацию на этом устройстве». Авторитетный курсор на клиенте: сервер не знает, доехала ли последняя страница |

## `auth_nonce` — таблицы больше нет

**С 2026-09-04 не существует.** Изначально предполагалась здесь, но по факту
реализации nonce мобильного входа живёт в памяти процесса google-auth
(`AppState::issued_nonces`) — тем же приёмом, что уже там есть у `pending`/
`pending_signups`: живёт секунды в рамках одного входа, заводить таблицу и
миграцию ради этого не понадобилось. См. README google-auth, «Мобильный
вход».

## `sync_push_batch`

Идемпотентность отправки. `batch_id` генерирует клиент; повтор с тем же id
возвращает сохранённый `response` (выданные `seq` и список конфликтов), ничего не
применяя.

Ключ на батч, а не на строку: батч и так применяется одной транзакцией, и записать
один факт дешевле, чем разбирать построчно, где своя правка, а где чужая. Строки
живут порядка недели — клиент, не получивший ответ неделю назад, давно пересобрал
батч заново.

## `blob`

Содержимое, адресуемое по SHA-256. Сейчас это только изображения иконок.

| Поле | Тип | Описание |
| --- | --- | --- |
| `sha256` | bytea PK, CHECK 32 байта | |
| `bytes` | bytea NOT NULL, CHECK 1 байт … 1 МиБ | Ограничение — защита от заливки произвольных файлов через API иконок |
| `created_at` | timestamptz NOT NULL | |

Одинаковая картинка у разных пользователей хранится один раз, а клиент по хешу
заранее знает, что файл у него уже есть, и не качает повторно. При синке через
мобильный интернет это основная экономия трафика — всё остальное в протоколе это
JSON на сотни байт.

Строк без владельца здесь не избежать: `ledger_id` нет, содержимое общее. Право
прочитать конкретный blob проверяет **приложение** — по наличию видимой
запрашивающему `icon` с этим `content_sha256`. В схеме такой проверки быть не
может: у контент-адресуемого хранилища владельца не существует.

# Справочные таблицы

Область видимости у всех одна и та же: `ledger_id IS NULL` — общая строка,
заполненный — своя. При совпадении естественного ключа своя строка перекрывает
общую.

## `icon`

| Поле | Тип | Описание |
| --- | --- | --- |
| `name` | text NOT NULL | Подпись иконки. В клиентской схеме колонка объявлена `INT`, но SQLite тип не навязывает: все 84 значения в реальной базе — строки (`unknown`, `Flag Euro`, `Babysitting`). Зеркалить объявленный тип было бы зеркалированием намерения, а не данных |
| `content_sha256` | bytea NOT NULL → `blob.sha256` | `ON DELETE RESTRICT`: пока иконка ссылается на содержимое, удалить его нельзя. Сборка мусора по `blob` — задача по расписанию, а не побочный эффект |
| `icon_type` | smallint NOT NULL, CHECK `>= 0` | `1` — флаг, **всё остальное** — категория, ровно как в клиенте. Сужать до `(0, 1)` нельзя: в реальной базе 62 иконки из 84 имеют значение `2` — наследие ранней схемы, которое приложение показывает без нареканий |

`account.icon_uuid` и `currency.icon_uuid` объявлены `ON DELETE RESTRICT` — как в
клиенте, где удаление используемой иконки падает на внешнем ключе. В серверной
модели удаление мягкое, так что `RESTRICT` здесь страховка от жёсткого `DELETE`,
а не рабочий механизм: «иконка используется» проверяет приложение.

## `currency`

| Поле | Тип | Описание |
| --- | --- | --- |
| `name`, `iso_code` | text NOT NULL | Уникальны в пределах своей области видимости |
| `icon_uuid` | uuid NOT NULL → `icon.uuid` | Иконка-флаг |
| `symbol` | text NOT NULL | `$`, `€`, … |
| `"precision"` | smallint NOT NULL DEFAULT 2, CHECK 0…8 | Знаков в суммах этой валюты. На клиенте определяет и вывод (`AdapterUtils.getFormat`), и `InputFilter` в полях суммы. Верхняя граница связана с масштабом `operation.amount` |

Имя в кавычках — страховка: `PRECISION` в PostgreSQL незарезервировано, но
встречается внутри `DOUBLE PRECISION`. Идентификатор остаётся строчным, поэтому в
запросах колонку можно писать без кавычек.

Схема **не** запрещает пользователю завести локальный `USD` рядом с общим — два
частичных индекса по разным областям такое пропускают. Это проверяет приложение;
клиент при совпадении кода предпочитает свою строку.

## `currency_pair`

Пара с направлением «база → квота» и своей точностью курса.

| Поле | Тип | Описание |
| --- | --- | --- |
| `symbol` | text NOT NULL | Уникален в своей области |
| `base_currency_uuid`, `quote_currency_uuid` | uuid NOT NULL → `currency.uuid` | `CHECK` запрещает пару валюты с собой |
| `"precision"` | smallint NOT NULL DEFAULT 5, CHECK 0…10 | Знаков в курсе |

Внешние ключи на `currency` простые, без `ledger_id`: валюта бывает и общей, и
локальной, поэтому составной ключ арендатора здесь не построить. Что пара леджера
не ссылается на чужую валюту — **проверка приложения**.

## `currency_pair_rate`

Курс пары на дату: quote за 1 base. Самая большая таблица базы — история по всем
парам за все годы.

| Поле | Тип | Описание |
| --- | --- | --- |
| `currency_pair_uuid` | uuid NOT NULL → `currency_pair.uuid` | |
| `"date"` | date NOT NULL | `date`, а не клиентский DATETIME: курс — величина на день, и две записи на одну дату с разным временем невозможны |
| `rate` | numeric(24,10) NOT NULL, CHECK > 0 | Ноль или минус уронили бы обратный курс `1.0 / rate` |

Масштаб шире клиентского `DECIMAL(12,5)` и шире максимального
`currency_pair.precision`: сервер не должен терять точность источника, даже если
пара отображается с пятью знаками.

Два уникальных индекса на естественный ключ — по одному на область видимости.
Один общий индекс запретил бы ручной ввод курса на дату, для которой уже есть
общий, то есть ровно тот случай, для которого ручной ввод и нужен.

`ix_currency_pair_rate_lookup` — по `(currency_pair_uuid, "date" DESC)`: курс
всегда ищется как `max(date)` не позже нужной, такой индекс отдаёт его первой
строкой.

## `currency_conversion`

Ручное переопределение маршрута пересчёта, когда прямой пары нет.

**В клиенте таблица создаётся и остаётся пустой** — ни один код-путь в неё не
пишет, а `v_currency_conversion` всегда резолвит курс через `currency_pair`.
Заведена ради полноты зеркала: если клиент начнёт её заполнять, синку не придётся
добавлять сущность на ходу.

| Поле | Тип | Описание |
| --- | --- | --- |
| `from_currency_uuid`, `to_currency_uuid` | uuid NOT NULL → `currency.uuid` | `CHECK` запрещает пересчёт валюты в себя |
| `num` | smallint NOT NULL DEFAULT 0 | Номер альтернативного маршрута между одной парой валют |
| `currency_pair_uuid` | uuid NOT NULL → `currency_pair.uuid` | |
| `is_reverse` | boolean NOT NULL DEFAULT false | Признак «пара развёрнута» |

# Данные леджера

У всех `ledger_id NOT NULL` — общих счётов и операций не бывает.

## `account`

Единая таблица кошельков и категорий, как в клиенте: строка становится кошельком,
если для того же `uuid` есть строка в `account_operating` (с v76 то же самое
говорит `kind` — см. ниже).

| Поле | Тип | Описание |
| --- | --- | --- |
| `name` | text NOT NULL | Уникально среди живых счётов леджера |
| `comment` | text NOT NULL DEFAULT `''` | |
| `icon_uuid` | uuid NOT NULL → `icon.uuid` | |
| `is_archived` | boolean NOT NULL DEFAULT false | Вместо клиентского `INT DEFAULT 0`. Признак только для интерфейса: в расчётах архивный счёт участвует наравне с остальными, иначе архивация молча меняла бы итоги за прошлые периоды |
| `system_kind` | smallint NOT NULL DEFAULT 0, `CHECK IN (0,1,2)` | Явный признак системной категории вместо распознавания по `name` (обсуждение 2026-09-09): 0 = обычная, 1 = `Transfer`, 2 = `Transfer commission` — см. `AccountItem.SystemKind` на клиенте |
| `kind` | smallint NOT NULL DEFAULT 0, `CHECK IN (0,1)` | Явный признак «кошелёк или категория» (обсуждение 2026-09-09), тем же приёмом, что `system_kind`: 0 = категория, 1 = кошелёк — см. `AccountItem.Kind` на клиенте. Дублирует наличие строки в `account_operating`, проставляется один раз при создании строки и дальше не меняется |

Первичный ключ `pk_account (ledger_id, uuid)` — цель составных внешних ключей из
`operation`, благодаря чему сослаться на счёт чужого леджера невозможно даже при
враждебном клиенте.

`uq_account_name (ledger_id, name) WHERE deleted_at IS NULL` — то самое место, где
ловится главный конфликт офлайновой работы: два устройства независимо создали
«Продукты». Второй push нарушает индекс, сервер отвечает 409 с `uuid` выжившей
строки, клиент переклеивает свои операции на него и снимает локальный дубль. Это
единственный сценарий, в котором клиент переписывает локальные ссылки.

Системные категории (`Transfer`, `Transfer commission`) раньше признака в схеме
не имели вообще и опознавались по `name` — хрупко вдвойне, поскольку `name`
единственное уникальное поле счёта, и пользователь мог переименовать системную
категорию, молча сняв с неё защиту от удаления. `system_kind` — постоянный
признак; сравнение по имени осталось только в миграции, которая бэкфиллит его на
уже существующих строках.

## `account_operating`

Расширение `account` для кошельков: строка есть — счёт операционный, есть валюта и
баланс; строки нет — это категория. `uuid` всегда равен `account.uuid`.

| Поле | Тип | Описание |
| --- | --- | --- |
| `uuid` | uuid PK | Не генерируется отдельно — берётся у счёта |
| `currency_uuid` | uuid NOT NULL → `currency.uuid` | |

Отдельная синхронизируемая сущность со своими `seq` и `deleted_at`, а не колонка в
`account`: смена валюты кошелька и снятие «операционности» должны ехать между
устройствами как самостоятельные изменения.

Составной внешний ключ `(ledger_id, uuid) → account (ledger_id, uuid)` заодно
делает `ledger_id` здесь достоверным без собственной ссылки на `ledger`.

У категории своей валюты нет и быть не может: валюта операции по категории
определяется второй стороной проводки, то есть кошельком.

## `operation`

Единственная таблица транзакций. Любая операция — перевод между двумя `account`:
расход это «кошелёк → категория», доход «категория → кошелёк», перевод
«кошелёк → кошелёк».

| Поле | Тип | Описание |
| --- | --- | --- |
| `"date"` | timestamp NOT NULL | **Без** часового пояса, намеренно — см. [`../README.md`](../README.md), раздел «Даты» |
| `acc_fr_uuid`, `acc_to_uuid` | uuid NOT NULL | Составные FK `(ledger_id, …) → account`, `NO ACTION`: счёт с операциями жёстко не удалить |
| `amount` | numeric(20,8) NOT NULL, CHECK ≥ 0 | Всегда положительное; направление задаёт пара `acc_fr`/`acc_to`, знак — только на экране |
| `comment` | text NOT NULL DEFAULT `''` | Свободный текст, пустая строка допустима |

`ck_operation_sides` запрещает проводку саму в себя — в клиенте это отсекает
только валидация экрана.

Индексы: лента и отчёты идут по `(ledger_id, "date" DESC)`; баланс кошелька —
разница поступлений и списаний до даты, то есть два независимых обхода, отсюда
отдельные индексы по `acc_fr_uuid` и `acc_to_uuid`. Все три частичные, по живым
строкам.

## `operation_link`

Связь проводок, которые пользователь завёл одной операцией, а база хранит
несколькими: разновалютный перевод (две ноги через системную категорию `Transfer`)
и комиссия за перевод. Появилась в клиенте в v71, потому что у `operation` одна
колонка `amount`, а разновалютному переводу нужны две суммы.

| Поле | Тип | Описание |
| --- | --- | --- |
| `uuid` | uuid PK | Суррогат вместо клиентской пары `(main_id, link_id)`: синку нужна одна колонка идентичности на строку |
| `main_uuid` | uuid NOT NULL | **Всегда** проводка списания с кошелька-источника; по ней находится вся операция целиком |
| `link_uuid` | uuid NOT NULL | Вторая нога или комиссия |
| `type` | smallint NOT NULL DEFAULT 0, `CHECK IN (0,1)` | Явная роль связки (обсуждение 2026-09-09), тем же приёмом, что `account.system_kind`: `0` — нога валютного перевода, `1` — комиссия — см. `OperationItem.LinkType` на клиенте. Заменяет прежний вывод по `system_kind` счёта-источника связанной проводки |

Естественная пара осталась уникальной (`uq_operation_link_natural`), плюс
`ix_operation_link_link` для обратного обхода «по проводке найти группу».

Ради этой таблицы push применяется одной транзакцией: если вторая нога или
комиссия доедут отдельно от первой, второе устройство увидит половину операции и
баланс кошелька разойдётся. Сама группа при удалении не снимается — это задача
приложения, как и в клиенте (см. [`android-wallet/docs/TODO_transfers.md`](https://github.com/WalletTransactions/android-wallet/blob/main/docs/TODO_transfers.md)).
