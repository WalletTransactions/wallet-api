# Схема серверной базы (PostgreSQL)

DDL серверной части: та же предметная область, что в
[`../client`](https://github.com/WalletTransactions/android-wallet/tree/main/schema), плюс всё, чего в локальной базе быть не
может — владение данными, идентичность пользователя и версии строк для
синхронизации.

Требуется **PostgreSQL 13+** (`gen_random_uuid()` без `pgcrypto`); проверено на 18.4.

```bash
psql -v ON_ERROR_STOP=1 -f wallet-api/schema/apply.sql
```

[`apply.sql`](apply.sql) содержит только включения `\ir` в порядке зависимостей —
второй копии DDL в репозитории нет намеренно, копии расходятся молча.

**Статус проверки.** Схема развёрнута с нуля на PostgreSQL 18.4, поведение
проверено на живой базе, а не только по тексту:

| Что подтверждено | Проверка |
| --- | --- |
| `next_seq` монотонна, потоки `ledger` и `reference` независимы | два вызова подряд, сверка с номером соседнего потока |
| Составной FK не пускает ссылку в чужой леджер | операция в одном леджере на счёт другого — отказ по FK |
| Имя счёта уникально среди живых, tombstone его освобождает | дубль отклонён; после `deleted_at` то же имя вставляется |
| Одноимённые счёта в разных леджерах сосуществуют | вставка в соседний леджер проходит |
| Локальная валюта не конфликтует с общей того же ISO-кода | обе строки живут; второй общей — отказ |
| Ручной курс сосуществует с общим на ту же дату | обе строки живут; второй общий на ту же дату — отказ |
| Триггер `updated_at` срабатывает | метка после `UPDATE` больше прежней |
| Ужесточённые `CHECK` работают | отрицательная сумма, проводка сама в себя, `icon_type = 2`, нулевой курс, пустой blob — все отклонены |
| Владелец леджера ровно один | второй `owner` отклонён |
| Связь проводок создаётся, самоссылка запрещена | вставка группы и отказ на `main = link` |
| Операция на мягко удалённый счёт остаётся видимой в `v_operation` | счёт снят `deleted_at`, операция на месте |
| Изоляция арендатора в представлениях | `v_operation` чужого леджера пуста |
| Пара развёрнута в оба направления, курс валюты в себя равен 1 | `v_currency_conversion`, `v_currency_conversion_rate` |
| Ручной курс леджера перекрывает общий на ту же дату | выбор по `ORDER BY date DESC, (ledger_id IS NULL)` |
| Без курса `amount_eq` равен `NULL`, а не сумме по курсу 1:1 | пересчёт в валюту, к которой нет пары |

Первый прогон нашёл одну ошибку — в порядке `apply.sql`: тело SQL-функции
разбирается в момент `CREATE FUNCTION`, поэтому `next_seq()` не могла быть создана
до своей таблицы. Порядок исправлен, ограничение описано комментарием в самом
файле.

**Повторно проверено 2026-09-04** на живой базе против реальной миграции
(`wallet-api/migrations/000002_ledger_sync.up.sql`, упрощённые
`app_user`/`device`, без `auth_nonce` — см. «Идентичность и токены» ниже):
все пункты таблицы выше подтвердились и на адаптированной схеме, плюс
`wallet_reader` читает, но не пишет (`INSERT` отклонён по правам).

**Ещё раз проверено 2026-09-04** после добавления `COMMENT ON TABLE`/`COMMENT
ON COLUMN` по всем таблицам (см. `table/*.sql` — тот же текст продублирован в
`wallet-api/migrations/000003_comments.up.sql`, отдельной
миграцией: 000001/000002 уже накачены на живую базу, а `COMMENT ON` — такое
же настоящее изменение схемы, как и любое другое, только повторно
golang-migrate его не применит). `apply.sql` целиком прогнан на чистой базе
до конца, `pg_description` подтверждает число комментариев (133 — без демо-
таблицы `wallets`, которой в этом каталоге нет, см. `apply.sql`, "источник
истины"), 000003 применена и откачена на отдельной базе с тем же результатом
(0 комментариев после `down`).

Этот же прогон нашёл независимую, более старую ошибку: `view/v_account_operating.sql`
физически содержал не свою вьюху, а дубль `v_currency_conversion_rate` — сама
`v_account_operating` (на которую ссылается `f_balance_to_date`) была
заведена только в реальной миграции и отсутствовала в этом каталоге вообще.
`apply.sql` с этим файлом падал на `v_currency_conversion cc does not exist`
(вьюха, которую файл ошибочно пытался создать раньше своей зависимости).
Исправлено — файл переписан на содержимое из миграции (простой `JOIN`, не
`LEFT JOIN`, как ошибочно описывало `view/README.md`, — см. `v_account_expanse.sql`
для обратного, `LEFT JOIN`-варианта).

## Структура папки

| Папка | Содержимое |
| --- | --- |
| `table/` | `CREATE TABLE` с индексами и триггерами по каждой таблице — см. [table/README.md](table/README.md) |
| `view/` | Порт клиентских представлений с арендатором и областями видимости — см. [view/README.md](view/README.md) |
| `function/` | Служебные `next_seq` и `set_updated_at` плюс отчётные `f_balance_to_date`, `f_income_for_period`, `f_expanse_for_period` — порт `client/select/`, см. [function/README.md](function/README.md) |
| `role/` | Роли базы и их гранты; пока одна — `wallet_reader` для сервиса отчётов, см. [role/README.md](role/README.md) |

Представления существуют **для сервиса отчётов**, а не для клиента. Приложение
офлайновое и обязано считать эквивалент и балансы само — это не обсуждается, и
`WalletDbLoader.LoadBalancesPerWallet` остаётся единственной реализацией на его
стороне. Но у сервиса отчётов своего Java-слоя нет и не будет (прототип на
Python удалён 2026-09-30;
логика переезжает в C++ вместе с остальными сервисами, см.
[wallet-infra/README.md](https://github.com/WalletTransactions/wallet-infra/blob/main/README.md)): различать кошельки
от категорий и искать курс на дату ему придётся в SQL, и лучше это будет один
разобранный набор вьюх, чем запросы, собираемые в каждом эндпоинте заново.

Отсюда правило, за которым надо следить: реализаций расчёта ровно две — по одной
на сторону. Появится третья — цифры разойдутся, и разойдутся молча.

## Что здесь принципиально иначе, чем в клиенте

### Идентичность строки — `uuid`, а не автоинкремент

В клиенте `_id INTEGER PRIMARY KEY AUTOINCREMENT`, и два устройства неизбежно
выдадут один и тот же номер разным операциям. Поэтому идентичность
синхронизируемой строки — `uuid`, который **генерирует клиент** при создании
записи, ещё в офлайне.

Локальный `_id` при этом никуда не девается и на сервер не попадает: адаптеры,
`MainActivity.transactions` и `WalletDbLoader` продолжают работать с int. Входящая
строка ищется по `uuid`; нет такой — INSERT с новым локальным `_id`, есть —
UPDATE. Все ссылки в обмене (`acc_fr_uuid`, `icon_uuid`, …) резолвятся в локальные
`_id` уже на клиенте.

Там, где в клиенте естественный ключ составной (`currency_pair_rate`,
`currency_conversion`, `operation_link`), первичным всё равно стал суррогатный
`uuid`, а составной ключ остался уникальным индексом. Причина в протоколе:
outbox на клиенте, разрешение конфликтов и ответ на push адресуют строку **одной**
колонкой.

### Версия строки — `seq`, а не время

Каждая синхронизируемая таблица несёт `seq bigint`. Клиент хранит курсор и
запрашивает «всё, у чего `seq` больше моего». Значение выдаёт
[`next_seq()`](function/next_seq.sql) из счётчика в `change_stream` — **не**
`SEQUENCE` и **не** `now()`.

Почему не последовательность: номер у неё выдаётся вне транзакции, поэтому строка
с `seq = 5` может закоммититься раньше, чем `seq = 4`. Читатель, идущий по
курсору, в этот момент увидит 5, сдвинет курсор и за 4 уже никогда не вернётся —
операция пропадёт молча, а сумма по счёту разойдётся с другим устройством.
Счётчик в таблице инкрементируется в той же транзакции и берёт блокировку строки,
так что порядок `seq` совпадает с порядком коммитов.

Почему не время: устройство может месяц пролежать офлайн со съехавшими часами.
Ни одно решение о конфликте по времени не принимается. `updated_at` есть, но
только для диагностики — его проставляет триггер, чтобы колонка не врала.

### Курсор и страницы

`seq` выдаётся **один на батч**, а не на строку: все изменения одной отправки
получают одно значение. Отсюда следует свойство, на которое опирается клиент —
**страница выборки никогда не разрезает атомарную группу**, потому что не
разрезает одинаковый `seq`. Сервер добирает строки до лимита и затем дотягивает
текущую группу `seq` до конца, поэтому курсор клиента — обычный `bigint`, без
составных значений.

Это важно именно для `operation_link`: если вторая нога разновалютного перевода
или комиссия доедут отдельно от первой, второе устройство увидит половину
операции.

### Потоков изменений два

| Поток | Что везёт | `ledger_id` |
| --- | --- | --- |
| `reference` (один на базу) | иконки из поставки, валюты, пары, курсы | `NULL` |
| `ledger` (по одному на леджер) | счёта, операции, свои иконки и валюты пользователя | заполнен |

Справочные таблицы держат обе области сразу: `ledger_id IS NULL` — строка общая,
заполненный — своя. Клиент хранит два курсора, а общий поток отдаётся всем
одинаково и кэшируется.

Уникальность в таких таблицах разъезжается на два частичных индекса — по одному
на область. Это не формальность: курс, введённый пользователем вручную, обязан
сосуществовать с общим курсом той же пары на ту же дату, иначе ручной ввод
ломается ровно там, где он и нужен. При совпадении своя строка перекрывает общую.

### Удаление — `deleted_at`, а не `DELETE`

`WalletDbCRUD.DeleteOperation`/`DeleteAccount` делают жёсткий `DELETE`, и такое
удаление до второго устройства не доедет: сообщать об исчезнувшей строке нечем.
Поэтому строки не удаляются, а помечаются, и tombstone едет как обычное изменение.

Побочная выгода: внешние ключи остаются целыми. Удалённая категория, на которую
ссылаются старые операции, физически на месте, и `NO ACTION` на
`operation.acc_fr_uuid` не мешает. Отдельная таблица tombstone'ов этого свойства
не дала бы.

Уникальные индексы по именам объявлены с `WHERE deleted_at IS NULL` — иначе имя
удалённой категории навсегда занято её же tombstone'ом.

### Деньги — `numeric`

В клиенте объявлено `DECIMAL(15,2)`, но SQLite тип игнорирует, а Java считает в
`double`. Сервер — первое место, где суммы действительно десятичные:
`operation.amount numeric(20,8)`, `currency_pair_rate.rate numeric(24,10)`.

Из этого следует требование к транспорту: в JSON суммы и курсы передаются
**строками**. Число с плавающей точкой в JSON вернуло бы ту же погрешность на
границе, и `numeric` в базе оказался бы декорацией.

### Даты

`operation.date` — `timestamp` **без** часового пояса. Это бизнес-дата, по которой
считаются периоды, балансы и курс на дату; она приходит от клиента в его локальном
времени и такой же хранится. Перевод в UTC сдвинул бы часть операций через границу
суток и разъехал отчёты за период между устройствами в разных поясах.

`currency_pair_rate.date` — `date`: курс это величина на день, и в такой колонке
невозможны две записи на одну дату с разным временем.

Служебные метки (`created_at`, `updated_at`, `deleted_at`, всё в auth-таблицах) —
наоборот, всегда `timestamptz`.

### Арендатор в ключе, а не в коде

`operation` ссылается на `account` **составным** внешним ключом
`(ledger_id, uuid)` — и он же первичный ключ `account`. Сослаться на счёт чужого
леджера невозможно даже при испорченном или враждебном клиенте. Альтернатива —
проверка в коде, которую однажды забудут в одном из путей записи.

Тот же составной ключ во всех четырёх таблицах данных леджера оставляет открытой
дверь к секционированию по `ledger_id`: PostgreSQL требует ключ секционирования
в каждом уникальном ограничении, и одиночный `uuid` в первичном ключе закрыл бы
эту возможность навсегда — а превращение обычной таблицы в секционированную, в
отличие от `SET SCHEMA`, требует перестройки с переливом данных. Сейчас в
секционировании нужды нет (при нынешних ~1 100 операциях в год на пользователя
разговор начинается на сотне тысяч пользователей), но страховка обошлась в ноль:
все входящие внешние ключи и так были составными.

Там, где ссылка идёт на справочную таблицу (`icon`, `currency`), составной ключ
не построить: строка бывает и общей, и локальной. Эти проверки остаются за
приложением и перечислены в [table/README.md](table/README.md).

Row-level security не включается: все запросы и так идут через один слой доступа,
который знает `ledger_id` из токена, а RLS добавила бы второй набор правил,
расходящийся с первым.

### Строже клиента

Два ограничения отвергнут данные, которые локальная база принимает молча:

| Ограничение | Что отсекает |
| --- | --- |
| `operation.amount >= 0` | направление задаётся парой `acc_fr`/`acc_to`, минус в сумме означает ошибку клиента |
| `operation.acc_fr_uuid <> acc_to_uuid` | проводка сама в себя; в клиенте это отсекает только валидация экрана |

Оба проверены на реальных данных: в 8 442 операциях нарушений нет ни одного.
Сервер — последнее место, где ошибку в деньгах ещё можно заметить, поэтому они
остаются.

А вот третье такое ограничение, `icon.icon_type IN (0, 1)`, здесь было и **снято**.
`Icon.IconType` в коде знает только `CATEGORY(0)` и `FLAG(1)`, но в реальной базе
62 иконки из 84 имеют значение `2` — наследие ранней схемы, которое приложение
показывает без нареканий по правилу «1 это флаг, всё остальное категория».
Ограничение отвергло бы три четверти иконок при первой же загрузке. Урок общий:
ужесточать имеет смысл там, где нарушение означает испорченные деньги, а не там,
где схема просто аккуратнее кода.

Отдельный случай — **схлопывание курсов в тип `date`**. В клиенте ключ
`(currency_pair_id, date)`, где `date` это текст, поэтому `'2020-09-02'` и
`'2020-09-02 00:00'` считаются разными ключами: в базе нашлось 9 таких пар, и
курсы в них различаются. Клиент разрешает их как `max(date)`, то есть побеждает
строка со временем — и при переносе на сервер нужно сохранять именно её, иначе
девять курсов молча изменятся и отчёты за 2020 год разъедутся.

## Идентичность и токены

Пароля в схеме нет и токены здесь не выпускаются вообще — вся аутентификация,
выпуск и ротация токенов централизована в `google-auth` (см. его
README, «Мобильный вход» и «Детали устройства»). `app_user.id` и
`device.id` — это claim'ы уже проверенного access-JWT (`sub` и `device_id`
соответственно), а не идентичность, которую порождает эта база: третий слой
идентичности поверх google-auth (свой `google_sub`, своя ротация
refresh-токенов в `device`) был спроектирован здесь изначально, но по факту
реализации (2026-09-04) оказался лишним — см. `table/app_user.sql` и
`table/device.sql`. Почта хранится для показа и не участвует в решениях о
доступе.

`ledger_member` заведён с первого дня, даже если пользователь один: добавить
общий кошелёк позже — это одна строка, а сменить ключ арендатора — переписать
каждую таблицу и каждый индекс.

`sync_push_batch` — идемпотентность отправки. У офлайнового клиента повтор
неизбежен (батч доехал, ответ потерялся), и без записанного факта применения
повтор выглядит как чужая правка и возвращает 409 на собственную запись
пользователя.

## Правило для правок

То же, что в клиентской схеме, и по той же причине: **любое изменение схемы
попадает сюда в том же изменении** — файл в `table/`, строка в
[table/README.md](table/README.md) и, если поменялся порядок зависимостей,
[`apply.sql`](apply.sql). Новая таблица — это ещё и строка в гранте: права роли
выдаются списком, вычисляемым в момент прогона, поэтому таблица, добавленная
миграцией на живой базе, окажется невидимой для `wallet_reader`, пока не
отработает `ALTER DEFAULT PRIVILEGES` или повторный `GRANT` из
[`role/wallet_reader.sql`](role/wallet_reader.sql).

Пока сервиса нет, эти файлы — источник истины. Как появятся миграции (Alembic или
`sqlx migrate`), роли меняются: источником становятся миграции, а `wallet-api/schema/`
превращается в читаемое зеркало — ровно как `android-wallet/schema/` относится к
`WalletDbHelper`.

Изменение, затрагивающее синхронизируемое поле, почти всегда парное: правится и
здесь, и в клиентской схеме. Расхождение типов по такому полю — источник ошибок,
которые проявятся только на втором устройстве.

Правка любой функции/вьюхи, за которой стоят реальные данные, обязана быть
проверена интеграционными тестами отчётов
([`wallet-report/tests_integration/`](https://github.com/WalletTransactions/wallet-report/tree/main/tests_integration),
`bash run_local.sh`) — 20 тестов на реальной цепочке миграций и реальном
протоколе синка. Гоняется автоматически перед каждым коммитом, если он
трогает `wallet-api/schema/` или `wallet-infra/infra/db/migrations/` (см.
[`scripts/hooks/README.md`](../scripts/hooks/README.md), один раз
`git config core.hooksPath scripts/hooks`).

Отдельная ловушка при добавлении функции: тело на **SQL** разбирается сразу при
`CREATE FUNCTION`, поэтому такая функция обязана идти в `apply.sql` после всех
таблиц, к которым обращается. У **plpgsql** тело не разбирается, и такая функция
может стоять раньше — на этом и держится нынешний порядок
`set_updated_at → change_stream → next_seq`.
