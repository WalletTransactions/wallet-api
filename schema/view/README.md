# Представления

Порт вьюх из [`../../client/view`](https://github.com/WalletTransactions/android-wallet/tree/main/schema/view). Смысл каждой тот же —
разница только в трёх вещах, которые добавляет сервер, и они одинаковы для всех:

| Добавка | Как выглядит |
| --- | --- |
| Арендатор | `ledger_id` есть в каждой строке; джойны идут по составному ключу `(ledger_id, uuid)` |
| Мягкое удаление | `WHERE ... deleted_at IS NULL` — tombstone'ы не должны попадать в отчёты |
| Область видимости справочников | строка леджера перекрывает общую; `ledger_id IS NULL` значит «общая» |

Зачем они здесь вообще. В [`../README.md`](../README.md) записано, что балансы и
эквивалент считает клиент, и дублировать эту логику на сервере не следует. Это
по-прежнему так для **клиента**: он офлайновый и обязан считать сам. Вьюхи нужны
сервису отчётов (прототип на Python удалён 2026-09-30, логика
переезжает в C++, см. [wallet-infra/README.md](https://github.com/WalletTransactions/wallet-infra/blob/main/README.md)) — у него своего Java-слоя нет, и
различать кошельки от категорий или искать курс на дату ему придётся в SQL.
Отсюда же следует правило: расчёт баланса живёт в одном месте на каждой стороне,
и если цифры разойдутся — расходятся именно эти два, а не три.

## Разрешение области видимости

Главное отличие от клиента, которого там нет как понятия. Валюта, пара, курс и
переопределение маршрута бывают общими (`ledger_id IS NULL`) и собственными
(`ledger_id` заполнен), и собственная перекрывает общую.

Перекрытие сделано **не** в справочных вьюхах, а в точке выбора конкретного
курса — в `v_operation_eq`. Причина простая: чтобы перекрыть, надо знать леджер, а
у справочной вьюхи его взять неоткуда. Пришлось бы разворачивать каждую общую
строку на все леджеры, то есть городить декартово произведение со всей историей
курсов. Вместо этого справочные вьюхи отдают обе строки, помечая каждую своим
`ledger_id`, а выбор делает тот, кто знает леджер операции:

```sql
ORDER BY rr."date" DESC, (rr.ledger_id IS NULL)
LIMIT 1
```

`false` сортируется раньше `true`, поэтому при равной дате собственный курс
леджера побеждает общий.

## `v_account_operating`

```
account JOIN account_operating ON (ledger_id, uuid)
```

**Исправлено 2026-09-04**: этот раздел раньше описывал `LEFT JOIN` и "все
счета леджера, включая категории" — не совпадало с реальной вьюхой ни в
миграции, ни (на момент исправления) в файле `view/v_account_operating.sql`
самого каталога, который физически содержал не свою вьюху, а дубль
`v_currency_conversion_rate` (см. `../README.md`, "Статус проверки"). Файл
переписан на содержимое из `wallet-api/migrations/000002_ledger_sync.up.sql`.

Только счета, у которых ЕСТЬ строка в `account_operating` — то есть кошельки,
а не категории; обычный `JOIN`, не `LEFT JOIN`. Категории сюда не попадают
вообще (обратный фильтр — `v_account_expanse` ниже), поэтому `currency_uuid`
в этой вьюхе никогда не `NULL`.

| Поле | Источник |
| --- | --- |
| `ledger_id`, `uuid`, `name`, `comment`, `icon_uuid`, `is_archived` | `account` |
| `currency_uuid` | `account_operating` |
| `asset_type`, `include_in_net_worth` | живая строка `account_asset` (`LEFT JOIN`, 000033); `NULL` — не актив |
| `counterparty_uuid` | живая строка `account_debt` (`LEFT JOIN`, 000036, change `debts`); `NULL` — не долговой кошелёк |

## `v_account_expanse`

Обратный фильтр: счета без строки в `account_operating`, то есть категории.

В клиенте эта вьюха определена, но не используется — экраны фильтруют категории
через `AccountList` на стороне Java. На сервере такого слоя нет, поэтому здесь
она не декоративная.

## `v_currency_conversion`

Разворачивает каждую пару в **два** направления (`base → quote` и `quote → base`
с флагом `is_reverse`) и подмешивает переопределение из `currency_conversion`.
Запрос выше по стеку спрашивает курс `from → to`, не заботясь о том, в какую
сторону задана пара.

| Поле | Смысл |
| --- | --- |
| `ledger_id` | `NULL` — направление доступно всем |
| `from_currency_uuid/name/iso`, `to_currency_uuid/name/iso` | Валюты направления |
| `currency_pair_uuid` | Пара, из которой получено направление |
| `num` | Номер альтернативного маршрута; всегда `0` в текущих данных |
| `is_reverse` | `true`, если направление — перевёрнутая пара |

**Ограничение.** Переопределение присоединяется только в своей области видимости
(`IS NOT DISTINCT FROM`): своё переопределение поверх **общей** пары не
поддержано. Сделано намеренно — `currency_conversion` в клиенте всегда пуста
(см. [`../table/README.md`](../table/README.md)), и вводить непроверенную
семантику ради ненаполняемой таблицы незачем. Появятся данные — доопределим.

## `v_currency_conversion_rate`

Курс на дату по каждому направлению, с уже применённым `1/rate` для обратного,
плюс через `UNION ALL` — тождественный курс `1` валюты в саму себя с датой
`2000-01-01`.

Тождественный курс не украшение: благодаря ему пересчёт валюты в себя всегда
находит курс, и отдельная ветка «если валюты совпали» вызывающему коду не нужна.

| Поле | Смысл |
| --- | --- |
| `ledger_id` | Более узкая из двух областей: ручной курс делает строку строкой леджера |
| `from_*`, `to_*` | Валюты направления |
| `date` | Дата курса |
| `rate` | Курс `to` за 1 `from`, уже с учётом разворота пары |

Области видимости курса и направления могут различаться: ручной курс леджера
ставится и к общей паре — именно тот случай, ради которого уникальные индексы на
`currency_pair_rate` разнесены по областям. Джойн разрешает сочетание, когда хотя
бы одна сторона общая.

`is_reverse` и `num` наружу не выводятся, как и в клиенте: они использованы внутри
вычисления `rate`, и показывать их значило бы предлагать посчитать курс заново.

## `v_operation`

Операция с именами счетов, валютой и признаками «операционный ли счёт» с каждой
стороны.

| Поле | Смысл |
| --- | --- |
| `ledger_id`, `uuid`, `date`, `acc_fr_uuid`, `acc_to_uuid`, `amount`, `comment` | Из `operation` |
| `acc_fr_name`, `acc_to_name` | Имена счетов |
| `currency_uuid` | Валюта операционной стороны |
| `acc_from_is_operating`, `acc_to_is_operating` | `boolean`, а не `1`/`0`: в PostgreSQL для этого есть тип |

**Счета намеренно не фильтруются по `deleted_at`.** Клиент удаляет счёт физически,
поэтому у него такой ситуации нет; на сервере удаление мягкое, и живая операция
вполне может ссылаться на снятый счёт. Отсеки мы их — операция молча исчезла бы из
отчёта, а сумма за период занизилась. Фильтруется только сама операция.

## `v_operation_eq`

`v_operation` + курс на дату операции + сумма в эквиваленте, по строке на каждую
валюту эквивалента, видимую леджеру.

| Поле | Смысл |
| --- | --- |
| Все поля `v_operation` | |
| `to_currency_uuid` | Валюта эквивалента этой строки |
| `max_date_rate` | Дата найденного курса — последняя не позже даты операции |
| `rate` | Курс `currency_uuid → to_currency_uuid` на эту дату |
| `amount_eq` | `round(rate * amount, precision валюты эквивалента)`; `NULL`, если курса нет |

Два отличия от клиента, оба сознательные.

**Способ поиска курса.** Клиент делает `max(date)` с группировкой по дюжине полей
операции и джойном обратно за самим курсом. Здесь то же самое выражено боковым
соединением с `LIMIT 1`: смысл идентичен, группировки нет, а сортировка ложится на
индекс `ix_currency_pair_rate_lookup (currency_pair_uuid, "date" DESC)`.

**Округление по `precision` валюты эквивалента**, а не по зашитой двойке. Колонка
для этого и заведена; два знака врали бы для валюты с другой точностью.

Что осталось строго как в клиенте — **отсутствие `COALESCE` на курсе**. Подставить
сюда `1` означало бы, что строка без курса перестаёт быть `NULL`, кошелёк без курса
молча входит в итоги по курсу 1:1 и завышает их. `NULL` здесь читается как
«пересчитать нельзя», и отчёт обязан пометить такую сумму неполной — три состояния
эквивалента разобраны в [`android-wallet/docs/ARCHITECTURE.md`](https://github.com/WalletTransactions/android-wallet/blob/main/docs/ARCHITECTURE.md).

## Что не портировано

Два файла из клиентской папки — черновики, которые там не создаются и ни одним
запросом не используются:

- `v_account_operating_balance` — ранняя попытка расчёта, который живёт в
  `WalletDbLoader.LoadBalancesPerWallet`;
- `v_currency_conversion_max_date_rate` — пересчёт через несколько пар подряд
  (`EXP(SUM(LOG(rate)))`), зависит от `is_reverse`/`num`, которых
  `v_currency_conversion_rate` наружу не отдаёт, то есть не заработал бы и в
  клиенте.

Переносить неработающие черновики в новую схему смысла нет: понадобится
многопарный пересчёт — он будет написан под серверную модель, а не воскрешён.
