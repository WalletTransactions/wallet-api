# ledger-provisioning Specification

## Purpose
Как у пользователя появляются данные в wallet-api: без отдельной регистрации
сервис сам заводит пользователя, его личный леджер и устройство по claim'ам
уже проверенного токена и определяет, с каким леджером работает запрос.

## Requirements

### Requirement: Пользователь по sub токена
Сервис SHALL отождествлять пользователя с claim'ом `sub` токена google-auth и
не вести своей идентичности. При каждом провизионировании строка
пользователя создаётся или обновляет email из токена. Пустой email (у токена
Telegram-бота его нет) сохранённый не затирает.

#### Scenario: Токен без email
- **WHEN** пользователь с сохранённым email обращается к `/sync/push` токеном без claim'а `email`
- **THEN** сохранённый email не меняется

### Requirement: Личный леджер при первом обращении
Если у пользователя нет ни одного членства, провизионирование SHALL создать
леджер «Мой кошелёк» с пустым потоком изменений (`seq` = 0) и сделать
пользователя его владельцем (`owner`). Отдельного эндпоинта регистрации нет.

#### Scenario: Первый синк нового пользователя
- **WHEN** пользователь, которого сервис ещё не видел, вызывает `GET /sync/pull`
- **THEN** у него появляется леджер с ролью `owner`, и ответ несёт `ledger.ledger_id` этого леджера

### Requirement: Кто провизионирует
Леджер SHALL заводиться только путями записи и синка: `POST /sync/push`,
`GET /sync/pull` и `POST /api/currency-pairs`. `/api/ledger/*` и остальные
ручки `/api/currency-pairs*` леджер не создают: без него они отвечают `404`
или пустым списком (см. `ledger-sharing`, `currency-pairs-api`).
Для `POST /api/invites/accept` действуют свои правила (см. `ledger-sharing`).

#### Scenario: Список участников до первого синка
- **WHEN** пользователь без леджера вызывает `GET /api/ledger/members`
- **THEN** ответ `404`, леджер не создан

#### Scenario: Первая валютная пара с веба
- **WHEN** пользователь без леджера создаёт пару `POST /api/currency-pairs`
- **THEN** леджер создаётся, пара записывается в него

### Requirement: Один леджер на пользователя
Сервис SHALL работать с одним леджером пользователя. Текущий леджер —
членство с самой ранней датой вступления. `ledger_id` никогда не
принимается от клиента ни в пути, ни в теле, ни в параметрах.

#### Scenario: Клиент присылает чужой ledger_id
- **WHEN** строка в `POST /sync/push` несёт `ledger_id` чужого леджера
- **THEN** строка пишется в леджер вызывающего пользователя, присланный `ledger_id` игнорируется

### Requirement: Устройство синка
Для `/sync/push` и `/sync/pull` токен SHALL нести claim `device_id`. Иначе
ответ `403` с `{"error":"device_required"}`, и ничего не провизионируется.
Отсутствие токена проверяется раньше: тогда ответ `401`.

#### Scenario: Сессия браузера без device_id
- **WHEN** токен без `device_id` вызывает `GET /sync/pull`
- **THEN** ответ `403`, `error` = `device_required`

### Requirement: Учёт устройства
Каждое обращение к `/sync/*` с `device_id` SHALL создавать или обновлять
устройство: `last_seen_at` = сейчас, `platform` из claim'а токена, имя из
необязательного поля `device_name` тела запроса. Пустое имя ранее
известное не стирает. Некорректное тело на учёт устройства не влияет.

#### Scenario: Повторный вход с тем же устройством
- **WHEN** устройство с известным именем вызывает `GET /sync/pull` без тела
- **THEN** имя устройства сохраняется, `last_seen_at` обновляется

### Requirement: Роль в леджере
Провизионирование SHALL определять роль пользователя в текущем леджере
(`owner`, `member`, `reader`). От роли зависит только режим записи токеном
`expense:write` (см. `sync-push`).

#### Scenario: Участник с ролью читателя
- **WHEN** пользователь с ролью `reader` вызывает `/sync/pull`
- **THEN** получает данные леджера, в который его пригласили, а не новый личный леджер
