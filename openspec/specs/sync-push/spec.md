# sync-push Specification

## Purpose
Приём изменений от клиентов синка (телефоны, веб, Telegram-бот) через
`POST /sync/push` (`operationId: syncPush`): атомарное применение батча,
версия строк для потока изменений, идемпотентность и понятные клиенту
конфликты.

## Requirements

### Requirement: Состав запроса
Тело push SHALL быть JSON-объектом с непустым `batch_id` и объектом
`changes` вида `{"<таблица>": [строки]}` (схема — `openapi.yaml`,
`syncPush`). Синхронизируемые таблицы: `icon`, `currency`, `currency_pair`,
`currency_pair_rate`, `currency_conversion`, `account`, `account_operating`,
`account_asset`, `operation`, `operation_link`.

#### Scenario: Нет batch_id
- **WHEN** тело push не содержит `batch_id`
- **THEN** ответ `400`, ничего не применено

#### Scenario: Тело не JSON
- **WHEN** тело push не разбирается как JSON
- **THEN** ответ `400` с `error` = `invalid JSON body`

#### Scenario: Батч с признаком актива
- **WHEN** `changes` содержит массив `account_asset`
- **THEN** его строки применяются, а не пропускаются как неизвестная таблица

### Requirement: Неизвестные таблицы
В полном режиме (токен с `wallet:write`) таблицу, которой сервер не знает,
и значение таблицы, не являющееся массивом, сервер SHALL молча пропускать,
не отклоняя батч, чтобы клиент новее сервера не ломался.

#### Scenario: Клиент новее сервера
- **WHEN** `changes` содержит `operation` и неизвестную таблицу `budget`
- **THEN** операции применены, `budget` проигнорирован, ответ `200`

### Requirement: Атомарный батч с одним seq
Все строки батча SHALL применяться в одной транзакции и получать один
`seq` — следующий номер потока леджера. При успехе ответ `200`
`{"seq": <номер>, "conflicts": []}`. При любой ошибке не применяется ничего.

#### Scenario: Перевод с двумя ногами
- **WHEN** батч несёт две операции и связь `operation_link` между ними
- **THEN** все три строки получают один `seq` и видны в pull только вместе

### Requirement: Порядок применения по зависимостям
Таблицы батча SHALL применяться в порядке `icon`, `currency`,
`currency_pair`, `currency_pair_rate`, `currency_conversion`, `account`,
`account_operating`, `account_asset`, `operation`, `operation_link`,
независимо от порядка ключей в теле, чтобы ссылки внутри одного батча
разрешались.

#### Scenario: Новая валюта и кошелёк в ней одним батчем
- **WHEN** батч несёт новую `currency` и `account_operating`, ссылающуюся на неё
- **THEN** батч применяется без ошибки внешнего ключа

#### Scenario: Новый актив одним батчем
- **WHEN** батч несёт новые `account`, `account_operating` и `account_asset` одного кошелька
- **THEN** батч применяется без ошибки внешнего ключа

### Requirement: Строка — upsert по uuid
Каждая строка SHALL создаваться или обновляться по `uuid` в леджере
вызывающего. Сервер сам ставит `ledger_id`, `seq`, `updated_by` (устройство
токена) и `deleted_at`. `"deleted": true` — мягкое удаление с `deleted_at`
= время сервера, иначе `deleted_at` сбрасывается.

#### Scenario: Мягкое удаление счёта
- **WHEN** строка `account` приходит с `"deleted": true`
- **THEN** у счёта проставлен `deleted_at` временем сервера, строка уходит в поток как tombstone

### Requirement: Общие и чужие строки не перезаписываются
Строку справочника, которая с тем же `uuid` уже есть как общая
(`ledger_id IS NULL`) или в чужом леджере, push SHALL не менять. Строка
пропускается с записью warn `sync_push_foreign_row_skipped`, остальной батч
применяется. Клиент не может создать общую строку.

#### Scenario: Телефон вернул общую иконку
- **WHEN** push несёт `icon` с `uuid` общей иконки из потока справочников
- **THEN** общая иконка не изменена, её `seq` не тронут, ответ `200`

### Requirement: Форматы значений на границе
Суммы и курсы (`operation.amount`, `currency_pair_rate.rate`) SHALL
приниматься десятичными строками и сохраняться без двоичного округления.
`icon.content_sha256` принимается hex-строкой. `currency_pair_rate.date`
усекается до первых 10 символов (`YYYY-MM-DD`), время в нём отбрасывается.

#### Scenario: Курс с временем в дате
- **WHEN** `currency_pair_rate.date` = `2026-10-01T15:00:00`
- **THEN** курс записан на дату `2026-10-01`

### Requirement: Курс по естественному ключу
Своя строка `currency_pair_rate` SHALL сначала искаться по `uuid` в леджере
(так оживает и мягко удалённая), иначе upsert идёт по ключу (леджер, пара,
дата) среди живых строк, и последний push побеждает, включая `uuid`.

#### Scenario: Два устройства, одна дата
- **WHEN** два устройства офлайн записали курс одной пары на одну дату с разными `uuid`
- **THEN** в леджере одна живая строка на эту дату — из последнего push

### Requirement: Повтор батча
Повтор успешно применённого `batch_id` SHALL возвращать сохранённый ответ
`200` с тем же `seq`, ничего не применяя. Неуспешный исход не сохраняется:
повтор после `400`/`409` применяется заново.

#### Scenario: Повтор после таймаута
- **WHEN** клиент повторяет батч с тем же `batch_id` после успешного, но не дошедшего ответа
- **THEN** ответ `200` с тем же `seq`, новых версий строк нет

### Requirement: Конфликт имени счёта
Если имя счёта совпадает с живым счётом леджера (без учёта регистра, «ё» =
«е»), push SHALL отвечать `409` с `conflicts[]`: `table` = `account`,
`reason` = `duplicate_name`, `uuid` клиента и `existing_uuid` выжившего
счёта. Батч не применяется.

#### Scenario: «кафе» против «Кафе»
- **WHEN** push создаёт счёт «кафе», а в леджере есть живой счёт «Кафе»
- **THEN** ответ `409` с `existing_uuid` счёта «Кафе»

### Requirement: Дубль другого уникального ключа
Нарушение иного уникального ограничения SHALL давать `409`
`{"error":"duplicate_key","constraint":"<имя>"}` без `existing_uuid`, а не
`500`.

#### Scenario: Дубль имени иконки
- **WHEN** push создаёт иконку с именем, уже занятым в леджере
- **THEN** ответ `409`, `error` = `duplicate_key`, `constraint` называет индекс

### Requirement: Недостающая ссылка
Ссылка на строку, которой нет, SHALL давать `409`
`{"error":"missing_reference","detail":…}`. Для одноколоночного ключа
ответ также несёт `table` (где строки не нашлось) и `uuid`, чтобы клиент
дослал её. Для составного ключа есть только `detail`.

#### Scenario: Пара раньше своей валюты
- **WHEN** push несёт `currency_pair` со ссылкой на валюту, которой у сервера нет
- **THEN** ответ `409` с `table` = `currency` и `uuid` этой валюты; после досылки валюты батч проходит

#### Scenario: Иконка без загруженного содержимого
- **WHEN** push несёт `icon` с `content_sha256`, не загруженным через `/sync/blobs`
- **THEN** ответ `409`, `error` = `missing_reference`

### Requirement: Строка без обязательного поля
Строка без `uuid` или без бизнес-колонки своей таблицы, а также с полем
неожиданного типа или значением вне допустимого набора колонки SHALL давать
`400` `{"error":"invalid_row","detail":"<что не так>"}`. Батч откатывается.
Исключение — колонки, которые требования явно называют необязательными
(`currency.show_in_equivalent`): их отсутствие не ошибка, а неверный тип —
ошибка.

#### Scenario: Старый клиент без новой колонки
- **WHEN** строка `account` не несёт `kind`
- **THEN** ответ `400`, `error` = `invalid_row`, `detail` называет поле

#### Scenario: Необязательная колонка неверного типа
- **WHEN** строка `currency` несёт `show_in_equivalent` = `"yes"`
- **THEN** ответ `400`, `error` = `invalid_row`, `detail` называет `show_in_equivalent`, батч не применён

#### Scenario: Значение вне допустимого набора
- **WHEN** строка `account` несёт `system_kind` = `9`
- **THEN** ответ `400`, `error` = `invalid_row`, а не `500`

### Requirement: Режим «только новые операции»
Токен с `expense:write` без `wallet:write` SHALL писать только новые
операции: в `changes` только массив `operation`, без `deleted` ≠ `false`, и
ни одного уже существующего `uuid`. Нарушение — `403` с `error`:
`only_operation`, `delete_not_allowed` или `operation_exists` (+ `table`,
`uuid`). Батч откатывается.

#### Scenario: Попытка удалить операцию токеном бота
- **WHEN** токен `expense:write` присылает операцию с `"deleted": true`
- **THEN** ответ `403`, `error` = `delete_not_allowed`, ничего не применено

#### Scenario: Операция уже существует
- **WHEN** токен `expense:write` присылает операцию с `uuid`, который у леджера уже есть
- **THEN** ответ `403`, `error` = `operation_exists`, существующая операция не изменена

#### Scenario: Повтор батча бота
- **WHEN** токен `expense:write` повторяет успешно применённый `batch_id`
- **THEN** ответ `200` с сохранённым `seq`, а не `operation_exists`

### Requirement: Читатель не пишет через бота
Пользователю с ролью `reader` в токене режима «только новые операции»
push SHALL отвечать `403` `{"error":"reader_cannot_write"}` до применения
и до проверки повтора. Токен с `wallet:write` роль не проверяет.

#### Scenario: Читатель подтвердил трату в боте
- **WHEN** читатель леджера отправляет push токеном `expense:write`
- **THEN** ответ `403`, `error` = `reader_cannot_write`

### Requirement: Флаг эквивалента у валюты
Строка `currency` в push SHALL принимать необязательное булево
`show_in_equivalent`. Если ключ присутствует, значение сохраняется. Если
ключа нет, новая валюта получает `true`, а у существующей своей валюты
прежнее значение не меняется.

#### Scenario: Пользователь снял флаг
- **WHEN** push несёт свою `currency` с `show_in_equivalent: false`
- **THEN** у валюты сохранено `false`, строка уходит в поток леджера с новым `seq`

#### Scenario: Старый клиент без ключа, новая валюта
- **WHEN** push несёт новую `currency` без ключа `show_in_equivalent`
- **THEN** ответ `200`, у валюты `show_in_equivalent = true`

#### Scenario: Старый клиент без ключа, существующая валюта
- **WHEN** у своей валюты `show_in_equivalent = false`, и push несёт её правку без ключа `show_in_equivalent`
- **THEN** ответ `200`, остальные колонки обновлены, `show_in_equivalent` остаётся `false`

#### Scenario: Флаг у общей валюты
- **WHEN** push несёт `currency` с `uuid` общей валюты и `show_in_equivalent: false`
- **THEN** общая валюта не изменена (действует «Общие и чужие строки не перезаписываются»), ответ `200`

### Requirement: Удаление операции снимает её связи
Если после применения батча у живой связи `operation_link` удалена хотя бы
одна из операций (`main_uuid` или `link_uuid`), сервер SHALL в той же
транзакции мягко удалить эту связь с `seq` батча и `updated_by` устройства
батча. Проверяются связи операций, удалённых этим батчем, и связи, присланные
этим батчем живыми. Связи, у которых обе операции живы, MUST NOT меняться.
Ответ push при этом не меняется.

#### Scenario: Удалили перевод
- **WHEN** батч приносит `"deleted": true` для операции, у которой есть живая связь
- **THEN** связь удалена с `seq` этого батча, и pull с курсором до батча отдаёт её tombstone вместе с удалением операции

#### Scenario: Связь прислана живой после удаления операций
- **WHEN** батч приносит живую связь, обе операции которой на сервере уже удалены
- **THEN** связь сохранена удалённой, ответ — 200 с пустым `conflicts`

#### Scenario: Удалили только комиссию
- **WHEN** батч удаляет операцию-комиссию, а у главной операции есть ещё связь со второй ногой перевода
- **THEN** удалена только связь с комиссией, связь со второй ногой осталась живой

#### Scenario: Операции живы
- **WHEN** батч правит комментарий операции, у которой есть живая связь
- **THEN** связь не меняется: ни `deleted_at`, ни `seq`

### Requirement: Удаление кошелька снимает его признак актива
Если после применения батча у живой строки `account_asset` удалён кошелёк
(`account_operating`) или сам счёт (`account` с тем же uuid), сервер SHALL в
той же транзакции мягко удалить эту строку с `seq` батча и `updated_by`
устройства батча. Проверяются кошельки и счета, удалённые этим батчем, и
активы, присланные этим батчем живыми. Актив живого кошелька MUST NOT
меняться. Ответ push при этом не меняется.

#### Scenario: «Удалить данные» удалили кошелёк-актив
- **WHEN** батч приносит `"deleted": true` для `account` и `account_operating` кошелька с живым `account_asset`
- **THEN** актив удалён с `seq` этого батча, ответ — 200 с пустым `conflicts`

#### Scenario: Актив прислан живым после удаления кошелька
- **WHEN** батч приносит живой `account_asset`, кошелёк которого на сервере уже удалён
- **THEN** актив сохранён удалённым

#### Scenario: Переименовали кошелёк
- **WHEN** батч правит имя живого кошелька-актива
- **THEN** `account_asset` не меняется: ни `deleted_at`, ни `seq`
