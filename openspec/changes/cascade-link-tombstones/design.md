# Design

## Context

`operation_link (ledger_id, uuid, main_uuid, link_uuid, type, deleted_at, seq)`;
FK на `operation (ledger_id, uuid)` с `ON DELETE CASCADE` — каскад работает
только при физическом `DELETE` (чистка tombstone), а синк удаляет мягко.
Чистка tombstone (`build_purge_statements`) не трогает удалённую операцию, на
которую ссылается любая связь, — поэтому живая связь ещё и держит на сервере
удалённые операции вечно.

## Decisions

1. **Каскад на сервере, а не в клиентах.** Сервер — единая точка для Android,
   веба и будущих клиентов; поправить только Android не вычистило бы связи,
   удалённые с других устройств, и уже накопленные.
2. **Правило: связь мертва, если удалена хотя бы одна её операция.** Обе
   стороны связи осмысленны только вместе: комиссия без перевода и нога без
   пары в отчётах всё равно не участвуют (там требуются живые связь и операции).
3. **Где проверять.** Один `UPDATE` в конце `push_batch`, после всех upsert:
   ```sql
   UPDATE operation_link l
      SET deleted_at = now(), seq = $2, updated_by = $3
    WHERE l.ledger_id = $1 AND l.deleted_at IS NULL
      AND (l.main_uuid = ANY($4::uuid[]) OR l.link_uuid = ANY($4::uuid[])
           OR l.uuid = ANY($5::uuid[]))
      AND EXISTS (SELECT 1 FROM operation o
                   WHERE o.ledger_id = l.ledger_id
                     AND o.uuid IN (l.main_uuid, l.link_uuid)
                     AND o.deleted_at IS NOT NULL)
   ```
   `$4` — операции, пришедшие в батче с `"deleted": true`; `$5` — связи,
   пришедшие живыми. Оба пусты — запрос не выполняется. Ограничение по батчу,
   а не весь леджер: стоимость push не растёт с размером леджера; индексы
   `uq_operation_link_natural (ledger_id, main_uuid, link_uuid)` и
   `ix_operation_link_link (ledger_id, link_uuid)` покрывают оба поиска.
   Списки собирает чистая функция `link_cascade_inputs(changes)` — её и
   проверяет юнит-тест; uuid в литерал массива попадают уже после успешного
   upsert этих же строк, то есть заведомо валидные.
4. **seq и updated_by — батча.** Tombstone связи едет в pull тем же `seq`, что
   и удаление операции, одной страницей; `updated_by` — устройство батча.
   Ответ push не меняется (`conflicts` пуст): это следствие, а не отказ.
5. **Оживление операции связь не оживляет.** Клиент, вернувший операцию,
   пришлёт и связь заново — правило её пропустит, раз обе операции живы.
6. **Миграция 000034 — данные, без схемы.** Для каждого леджера с такими
   связями — `next_seq(ledger_id)` и мягкое удаление с этим `seq`. Откат
   (`down`) — пустой: восстанавливать живые связи удалённых операций незачем,
   а отличить их от удалённых пользователем нельзя.

## Risks / Trade-offs

- Устройство, которое ещё не прочитало удаление операции, получит удаление
  связи одновременно с ним — порядок внутри страницы по `seq` тот же, что у
  самого батча, отдельной гонки нет.
- Миграция на большом леджере — один `UPDATE` по связям леджера. Замер
  2026-11-10 на копии test `wallet_api` (1 255 живых связей, из них 973 —
  с удалёнными операциями): 57 мс, все 973 закрыты одним `seq`, 282 живы.
