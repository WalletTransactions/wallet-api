# Design

## Context

Мотивация — proposal.md, «Why»; решения по продукту зафиксированы ответами в
issue `.github-private#1` и общие для четырёх парных changes.

Что есть сейчас и на что опираемся:

- Счёт — строка `account`; кошельком его делает строка `account_operating`
  (наследование через общий PK `(ledger_id, uuid)`). `account.kind`
  дублирует это и не меняется после создания, поэтому категорию
  «Квартира» нельзя превратить в актив — перенос операций делает клиент
  (парный change android-wallet).
- `account.system_kind` закрыт CHECK `IN (0,1,2)` (миграция `000012`):
  1 — `Transfer`, 2 — `Transfer commission`.
- Синк описан одной таблицей `push_tables()` в `src/sync_repo.cpp`; pull
  берёт тот же список. Порядок применения батча — `kApplyOrder`, он же
  `TABLE_ORDER` в Android `SyncEngine`.
- Отсутствие бизнес-колонки в строке push даёт `400 invalid_row`
  (`row.at()` → `json::exception`). Нарушение CHECK (`23514`) сейчас не
  перехватывается и уходит в `500`.
- Неизвестную таблицу push в полном режиме молча пропускает.
- Отчётные функции живут в миграциях; при смене `RETURNS TABLE` прежние
  миграции делают `DROP FUNCTION` + `CREATE` + повторный `GRANT EXECUTE`
  (`000022`). wallet-report выбирает колонки функций по имени
  (`src/reports_repo.cpp`), не `SELECT *`.
- `wallet_reader` получает `SELECT` на все таблицы, включая будущие, через
  права по умолчанию.

## Goals / Non-Goals

**Goals:**
- Признак актива и категория «Переоценка» хранятся и синкаются без поломки
  клиентов, не знающих о них.
- Все отчётные функции дают одинаковый ответ на вопрос «что такое
  переоценка» и отдают признак актива, чтобы wallet-report мог считать
  итоги «ликвидные / капитал / всего с капиталом».

**Non-Goals:**
- Проверка минимальной версии клиента (`X-Client-Version`, `426`) — вне
  scope; принято допущение «все устройства обновляются вручную до выката»
  (ответ 5 в issue, вопрос о механизме вынесен туда же).
- Серверная миграция существующих категорий в активы — только клиент.
- Защита системных категорий от переименования или удаления на сервере:
  сегодня её нет и для `Transfer`, её держит клиент.
- Обязательства (ипотека), амортизация, гибрид с абсолютной оценкой.

## Decisions

### D1. `account_asset` ссылается на `account_operating`, а не на `account`

FK `(ledger_id, uuid) → account_operating (ledger_id, uuid) ON DELETE
CASCADE`. Так «актив только у кошелька» держит сама схема, без отдельной
проверки в push: строка на категории даёт `23503`, то есть уже
существующий `409 missing_reference` (ключ составной, поэтому только
`detail`, без `table`/`uuid`, — как у `account_operating → account`).
Каскад от удаления леджера идёт `account → account_operating →
account_asset` без новых `SET CONSTRAINTS` в `account_deletion_repo.cpp`.

Живость FK не проверяет: мягко удалённый `account_operating` со живой
строкой `account_asset` возможен. Отчёты считают активом только кошелёк,
у которого живы обе строки (см. D4), так что такое состояние безвредно.

*Альтернатива:* FK на `account` плюс проверка «есть `account_operating`» в
`push_batch`. Отклонено: ещё одна ветка кода и ещё один путь ошибки ради
того, что умеет FK.

### D2. Все три бизнес-колонки обязательны в push

`asset_type`, `include_in_net_worth`, `comment` — в `TableSpec::columns`,
как у остальных таблиц. Таблица новая, старых клиентов, которые слали бы её
без какого-то поля, нет. Механизм опциональных колонок (если его введёт
`currency-ui-tweaks`) здесь не нужен.

Связанная правка вне этой репы: тестовая копия синка
`wallet-report/src/sync_repo.cpp` (сид данных в интеграционных тестах
отчётов) тоже получает `account_asset` в `TableSpec` и в порядок
применения — делается в парном change wallet-report, порядок должен
совпадать с `kApplyOrder` здесь.

### D3. Нарушение CHECK — `400 invalid_row`

В `push_batch` ловим `sqlstate == "23514"` рядом с `23505`/`23503` и
отвечаем `400 {"error":"invalid_row","detail":…}` с именем ограничения.
Это закрывает `asset_type` вне `1..3` и `system_kind` вне `0..3` и чинит
общий случай: значение вне набора — ошибка протокола клиента, не
внутренняя поломка. Дельта `sync-push`, требование «Строка без
обязательного поля».

### D4. Признак актива — в `v_account_operating`

`CREATE OR REPLACE VIEW v_account_operating` с `LEFT JOIN account_asset aa
ON … AND aa.deleted_at IS NULL` и двумя новыми колонками в конце:
`asset_type` (`NULL` — ликвидный) и `include_in_net_worth` (`NULL` у
ликвидного). Добавление колонок в конец `CREATE OR REPLACE VIEW`
позволяет. Через этот вид кошельки берут `f_balance_to_date`,
`f_balance_to_dates` и `f_balance_series`, поэтому определение «что такое
актив» для балансов живёт в одном месте.

Каждая из трёх балансовых функций получает в конце `RETURNS TABLE` колонки
`asset_type smallint`, `include_in_net_worth boolean` → `DROP FUNCTION` +
`CREATE` + `GRANT EXECUTE`. `f_balance_series` отдаёт их `NULL` и в
пустом бакете (строка с `NULL` account-полями), как остальные account-поля.
Итоги «ликвидные / капитал / всего с капиталом» считает wallet-report по
этим колонкам. Отдельной итоговой функции не делаем: балансовые функции и
так отдают строку на кошелёк, а итог — `sum()` с признаком неполноты.

`f_wallet_turnover_for_period` признак актива **не** отдаёт: wallet-report
в `/wallet-turnover` и `/accounts` сам делает `LEFT JOIN account_asset`
(парный change). От wallet-api для этого нужен только явный
`GRANT SELECT ON account_asset TO wallet_reader` в миграции — права по
умолчанию его и так дают, но явный грант документирует зависимость и не
зависит от того, кем создана таблица. Сигнатура turnover меняется только
телом (исключение переоценки, D5) → `CREATE OR REPLACE`.

*Альтернатива:* отдельная функция «список активов», а балансы не трогать.
Отклонено: wallet-report пришлось бы склеивать два ответа по `uuid` в
каждом балансовом отчёте.

### D5. Переоценка определяется по категории, а не по проводке

Проводка — переоценка, если одна из её сторон — счёт с `system_kind = 3`.
Проверка — `NOT EXISTS (SELECT 1 FROM account r WHERE r.ledger_id =
p_ledger_id AND r.uuid IN (o.acc_fr_uuid, o.acc_to_uuid) AND r.system_kind
= 3)` прямо в функциях, **без** фильтра `deleted_at`: проводки мягко
удалённой «Переоценки» не должны задним числом стать доходом. Колонки
признака в `v_operation`/`v_operation_eq` не добавляем — эти виды
пересоздаёт `partition-operation-by-ledger`, лишнее пересечение ни к чему.

Где исключаем: `f_income_for_period`, `f_expanse_for_period`,
`f_expanse_by_category_for_period`, `f_income_expense_by_month`,
`f_expense_by_weekday_for_period`, `f_wallet_turnover_for_period`
(обороты и `incomplete`). Сигнатуры всех шести не меняются →
`CREATE OR REPLACE`. Ветки `transfer_net` не трогаем: ноги перевода через
`Transfer` к переоценке отношения не имеют.

*Альтернатива:* отдельная таблица-признак проводок переоценки (вариант B из
разбора) или вывод «категория ↔ актив». Первое — больше схемы и синка,
второе ломается на доходе, проведённом прямо на актив. Решение A3 из
issue.

### D6. `kind = 'revaluation'` в ленте

В `f_operations_for_period` первая ветка `CASE` — `'revaluation'`, если
сработал признак D5; дальше прежние `transfer`/`expense`/`income`.
Категория и кошелёк в строке заполняются, как у дохода/расхода (одна
сторона — категория «Переоценка», другая — актив). Сигнатура не меняется.
Если раньше влит `add-operations-filter-functions`, фильтр `kind` и
функция итога должны принимать `'revaluation'` — правится там же, в
миграции этого change.

### D7. `f_assets_for_period` — тождество «оценка = вложено + переоценка»

Сигнатура: `(p_ledger_id uuid, p_from timestamp, p_to timestamp,
p_eq_currency uuid)`, `STABLE PARALLEL SAFE`, `SECURITY INVOKER`, `GRANT
EXECUTE` для `wallet_reader`. Строка на каждый живой актив леджера (живы
`account`, `account_operating`, `account_asset`), включая проданные
(баланс 0) и архивные; `is_archived` отдаётся, фильтрует клиент.

| Колонка | Смысл |
| --- | --- |
| `account_uuid`, `account_name`, `is_archived`, `icon_sha256` | карточка актива |
| `asset_type`, `include_in_net_worth` | признаки из `account_asset` |
| `currency_uuid`, `symbol`, `"precision"` | валюта актива |
| `value` | оценка: баланс по всем проводкам с `date <= p_to` |
| `revaluation_total` | сумма проводок переоценки с `date <= p_to` (со знаком: к активу +, от актива −) |
| `revaluation_period` | то же за `p_from..p_to` включительно |
| `invested` | `value − revaluation_total`: всё, кроме переоценки, — покупка, ремонт, продажа, ноги разновалютного перевода через `Transfer` |
| `return_pct` | `(value / invested − 1) × 100`, в процентах; `NULL`, если `invested <= 0` |
| `value_eq`, `invested_eq`, `revaluation_total_eq`, `revaluation_period_eq` | те же суммы по одному курсу — последнему `<= p_to` к `p_eq_currency`; `NULL` без курса |

`invested` выводится вычитанием, а не отдельной суммой «переводов»: у
разновалютной покупки нога в актив идёт от категории `Transfer`, а не от
кошелька, и любая попытка перечислить «настоящие вложения» по виду
контрагента такие ноги теряет. Граница — включительно `p_to`, как у
периодных функций; балансовые функции берут «строго до даты», wallet-report
согласует это в парном change. Эквиваленты всех четырёх сумм берутся по
одному курсу на `p_to`, а не по курсам дат проводок: так тождество
`value_eq = invested_eq + revaluation_total_eq` сохраняется, а «вложено в
эквиваленте» означает «сколько вложенное стоит в валюте отчёта сейчас».
Имена колонок согласованы с парным change wallet-report (его design D4).

### D8. Номер миграции — следующий свободный

Один файл `0000NN_capital_assets.up.sql` / `.down.sql`. `000026` уже
заявлен `currency-ui-tweaks` и `purge-synced-tombstones`, номер выбирается
при реализации. Down: вернуть прежние определения функций и вида (из
предыдущей миграции, которая их задавала), `DROP TABLE account_asset`,
CHECK `system_kind IN (0,1,2)`. Down с уже существующими строками
`system_kind = 3` упадёт на CHECK — это ожидаемо, откат после начала учёта
требует ручного решения (см. Risks).

## Совместимость

| Клиент | Что видит после миграции |
| --- | --- |
| Android без поддержки | строки `account_asset` в pull игнорирует; актив — обычный кошелёк и входит в его итог; категория `system_kind = 3` → `fromValue` = `NONE` → проводки переоценки попадают в доход/расход этой версии; балансы верные |
| Android с поддержкой | полное поведение (парный change) |
| wallet-telegram | без изменений: шлёт только новые операции |
| wallet-report старой версии | работает: новые колонки функций в конце, читает по имени |

## Risks / Trade-offs

- [Android с активами выходит раньше сервера] → push молча пропускает
  неизвестную `account_asset` (требование «Неизвестные таблицы»), клиент
  снимает `dirty`, и признак не доедет никогда. → Выкат строго: миграция и
  wallet-api раньше APK; в парном change android-wallet — повторная отправка
  всех строк `account_asset` при первом синке после обновления как вторая
  линия.
- [Миграции конфликтуют с `add-operations-filter-functions` и
  `partition-operation-by-ledger`] → все три пересоздают отчётные функции.
  → Кто влит позже, берёт текущее определение функции из последней
  миграции и добавляет свою правку; задачи ниже начинаются с этой сверки.
- [Где-то забыли исключить переоценку — цифры молча разъедутся] → общий
  предикат D5 одинаковым текстом во всех шести функциях; интеграционные
  тесты wallet-report проверяют каждую функцию на леджере с переоценкой.
- [Правка прошлой покупки сдвигает смысл последующих Δ] → принято для A3
  (issue, «Минусы A»); гибрид с абсолютной оценкой — позже.
- [Откат миграции после начала учёта] → down падает на CHECK при живых
  `system_kind = 3`. → Откат только кода wallet-api; схему откатывать после
  выката не планируем.

## Migration Plan

1. Влить миграцию; накатить на test (`env-deploy`), прогнать
   интеграционные тесты wallet-api и wallet-report.
2. Выкатить wallet-api (новый `push_tables`) и wallet-report (парный
   change) в prod.
3. Обновить Android на всех устройствах (допущение ответа 5), затем веб.
4. Откат: wallet-api и wallet-report — предыдущим тегом; миграция назад —
   только пока нет строк `account_asset` и `system_kind = 3`.
