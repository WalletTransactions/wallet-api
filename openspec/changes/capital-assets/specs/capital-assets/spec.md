# Spec Delta

## Purpose

Хранение и синхронизация признака капитального актива у кошелька и
системной категории «Переоценка», на которых строится учёт капитальных
вложений во всех клиентах и отчётах.

## ADDED Requirements

### Requirement: Актив — кошелёк с живой строкой account_asset
Кошелёк SHALL считаться капитальным активом, пока у него есть строка
`account_asset` с тем же `uuid` и `deleted_at IS NULL`. Строка
`account_asset` допустима только для счёта, у которого есть строка
`account_operating`. Мягкое удаление строки `account_asset` возвращает
кошелёк в ликвидные, не трогая его операции и баланс.

#### Scenario: Пометить кошелёк активом
- **WHEN** push несёт `account_asset` с `uuid` существующего кошелька и `asset_type` = `1`
- **THEN** ответ `200`, а в отчётных функциях этот кошелёк отдаётся с `asset_type` = `1`

#### Scenario: Актив на категории
- **WHEN** push несёт `account_asset` с `uuid` счёта без строки `account_operating`
- **THEN** ответ `409`, `error` = `missing_reference`, батч не применён

#### Scenario: Снятие признака актива
- **WHEN** push несёт `account_asset` с `"deleted": true`
- **THEN** кошелёк снова отдаётся с `asset_type` = `NULL`, его операции и баланс не меняются

### Requirement: Закрытый набор значений актива
`account_asset.asset_type` SHALL принимать только `1` (недвижимость), `2`
(авто) или `3` (прочее). `include_in_net_worth` — логическое значение,
`comment` — строка. Все три поля обязательны в строке push.

#### Scenario: Неизвестный тип актива
- **WHEN** push несёт `account_asset` с `asset_type` = `4`
- **THEN** ответ `400`, `error` = `invalid_row`, батч не применён

#### Scenario: Строка без поля
- **WHEN** push несёт `account_asset` без `include_in_net_worth`
- **THEN** ответ `400`, `error` = `invalid_row`, `detail` называет поле

### Requirement: Системная категория «Переоценка»
`account.system_kind` SHALL принимать значение `3` — системная категория
«Переоценка». Операции между этой категорией и кошельком отчётные функции
считают переоценкой, а не доходом или расходом. Признак действует и у мягко
удалённой категории, чтобы её прошлые проводки не стали доходом задним
числом.

#### Scenario: Клиент создаёт категорию «Переоценка»
- **WHEN** push несёт `account` с `kind` = `0` и `system_kind` = `3`
- **THEN** ответ `200`, строка сохранена с `system_kind` = `3`

#### Scenario: Неизвестный признак
- **WHEN** push несёт `account` с `system_kind` = `4`
- **THEN** ответ `400`, `error` = `invalid_row`, батч не применён

### Requirement: Признак актива доезжает до всех устройств
Pull SHALL отдавать строки `account_asset` в потоке `ledger` тем же
порядком и форматом, что остальные синхронизируемые таблицы: полный набор
колонок, мягко удалённые — с заполненным `deleted_at`.

#### Scenario: Второе устройство узнаёт об активе
- **WHEN** одно устройство пометило кошелёк активом, а другое делает pull со старым курсором
- **THEN** поток `ledger` содержит в `changes.account_asset` эту строку с `asset_type`, `include_in_net_worth` и `comment`

### Requirement: Клиент без поддержки активов не ломается
Push без таблицы `account_asset` и с прежними значениями `system_kind`
SHALL приниматься как раньше. Клиент, не знающий `account_asset`, получает
её строки в pull и вправе их игнорировать: балансы и операции от этого не
меняются.

#### Scenario: Старый клиент после миграции
- **WHEN** после выката миграции клиент старой версии шлёт батч с `account`, `account_operating` и `operation`
- **THEN** ответ `200`, как до миграции
