# Design

## Context

- Поток (`change_stream`): `seq` растёт на каждый батч `push`; строки девяти
  таблиц синка несут `seq` и `deleted_at`. `pull` отдаёт строки с
  `seq > cursor`, tombstone в том числе.
- `device` провизионируется на каждом `/sync/*` (`provisioning.cpp`),
  `last_seen_at` обновляется там же. `device.last_ack_seq` есть с миграции
  000002, но никем не пишется; комментарий в 000003 называет его справочным.
- Android сохраняет курсор только после применения страницы
  (`SyncEngine.pullAll`), поэтому курсор в запросе — надёжное подтверждение
  всего, что до него. Именно ответ сервер не может считать доставленным,
  запрос — может.
- wallet-telegram зовёт только `/sync/push` и не читает поток.
- Ссылки между таблицами синка — `NO ACTION` (миграция 000025): удалить строку,
  на которую ссылаются, нельзя, транзакция упадёт.

## Goals / Non-Goals

**Goals:**
- Подтверждения устройств в базе, горизонт по каждому потоку, чистка без
  отдельного процесса.
- Отставшее устройство получает явный сигнал начать поток с нуля.

**Non-Goals:**
- Чистка `sync_push_batch` (идемпотентность push) и осиротевших `blob` —
  отдельная задача.
- Удаление «мёртвых» строк `device`: они просто перестают входить в горизонт.
- Изменения в wallet-report/wallet-web: они уже читают только живые строки.

## Decisions

**1. Подтверждение — курсор из запроса `pull`, а не отдельный ack-эндпоинт.**
Клиент уже шлёт ровно то, что сохранил. Новый эндпоинт — лишний запрос на
каждую страницу и ещё одно место, где можно ошибиться. Значение пишется как
есть, даже если меньше прежнего: устройство, начавшее с нуля, честно держит
горизонт на нуле до конца перезагрузки.

**2. `ledger_id` в запросе защищает от чужого курсора.** После смены леджера
Android первый запрос шлёт курсор старого леджера; без проверки он стал бы
подтверждением в новом. Параметр необязательный: старые клиенты продолжают
работать, их подтверждение пишется без проверки (как было бы и с ack-эндпоинтом).

**3. Горизонт — `min` по активным устройствам; активность — `last_seen_at` за
90 дней.** Срок — `SYNC_TOMBSTONE_DEVICE_TTL_DAYS` (по умолчанию 90). Устройства
с `NULL`-подтверждением (бот, ещё не читавшие) пропускаются: им tombstone не
нужны, новое устройство начинает с нуля и получает только живые строки.
Альтернатива «ждать всех» отвергнута пользователем: потерянный телефон держал
бы чистку вечно.

**4. Чистка — в `handle_pull` после ответа, с троттлингом через
`change_stream.purged_at`.** Отдельного планировщика в сервисе нет, заводить
поток ради раза в час избыточно. Условие «прошло больше часа» проверяется
атомарно (`UPDATE change_stream SET purged_at = now() WHERE id = $1 AND
(purged_at IS NULL OR purged_at < now() - interval '1 hour') RETURNING`), так что
два параллельных `pull` не чистят одновременно. Чистка идёт отдельной
транзакцией на отдельном соединении пула после того, как ответ сформирован;
исключение ловится и пишется в лог (`sync_tombstone_purge_failed`).
Выключатель — `SYNC_TOMBSTONE_PURGE=off`.

**5. Удаление по таблицам от листьев к корням с `NOT EXISTS` на каждую ссылку.**
Порядок: `operation_link`, `operation`, `account_operating`, `account`,
`currency_conversion`, `currency_pair_rate`, `currency_pair`, `currency`,
`icon`. В каждом `DELETE` — `deleted_at IS NOT NULL AND seq <= $horizon` и
`NOT EXISTS` по всем ссылающимся таблицам (живым и удалённым строкам).
Список ссылок — рядом с `pull_tables()` в `sync_repo.cpp`, юнит-тест сверяет
его со списком таблиц синка, чтобы новая таблица не забылась. Альтернатива
«удалять и ловить FK-ошибку построчно» — тысячи savepoint на большом леджере.

**6. `change_stream.purged_seq = max(purged_seq, horizon)`** в той же транзакции,
что и удаление. Строки, оставленные из-за ссылок, могут иметь `seq <= purged_seq`;
это безопасно: отставший клиент всё равно перезагружается с нуля.

**7. Сброс: `0 < cursor < purged_seq` → `reset: true, reset_reason: "purged"`.**
Поле `reset` уже есть и старые клиенты на него реагируют (тянут с нуля), просто
без вычистки локальных строк — у них останутся «призраки» удалённых строк
только на телефоне. Новая Android-версия на любой старт с нуля делает вычистку
(см. её change). Курсор 0 — не отставание.

**8. Поток справочников — тем же механизмом.** Колонка
`device.last_ack_reference_seq`, горизонт по всем устройствам. Удаления там
редкие, но код общий, а отдельный путь «справочники не чистим» пришлось бы
объяснять.

## Risks / Trade-offs

- [Старая Android-версия после сброса `purged` хранит удалённые строки локально]
  → сначала выкатывается Android с вычисткой, чистка на сервере включается
  после (`SYNC_TOMBSTONE_PURGE` по умолчанию `off` в первом релизе).
- [Устройство вне 90 дней вернулось с неотправленными правками строки, которую
  уже вычистили] → `push` такой правки создаст строку заново (так же, как сейчас
  правка поверх tombstone её «воскрешает»: upsert по uuid). Ссылка на
  вычищенный счёт вернёт `missing_reference`, клиент уже обрабатывает это.
- [Чистка большого леджера держит блокировки] → чистка одного потока за
  проход; `DELETE` по индексам `(ledger_id, seq)`; первая чистка после
  включения может быть крупной — замерить на копии прода.
- [Неверное подтверждение от бага клиента (курсор больше реально применённого)]
  → тот же риск уже есть: такой клиент и сейчас пропускает изменения.

## Migration Plan

1. Миграция 000026: `device.last_ack_reference_seq bigint`,
   `change_stream.purged_seq bigint NOT NULL DEFAULT 0`,
   `change_stream.purged_at timestamptz`; новый комментарий к
   `device.last_ack_seq`. Down — удалить колонки, вернуть комментарий.
2. Релиз wallet-api с записью подтверждений и `reset_reason`, чистка `off`.
3. Релиз Android с вычисткой при старте с нуля и параметром `ledger_id`.
4. Когда телефоны обновились — `SYNC_TOMBSTONE_PURGE=on`.
Откат: `SYNC_TOMBSTONE_PURGE=off`; вычищенное не вернуть, но и не нужно — его
уже никто не ждал.
