# Spec Delta

## Purpose

Как сервер физически хранит данные леджера (операции и их связи): по какому
признаку строки разнесены, что гарантировано коду и клиентам при любой смене
хранения и как такая смена выкатывается.

## ADDED Requirements

### Requirement: Операции секционированы по леджеру
Таблицы `operation` и `operation_link` MUST быть секционированы хешем по
`ledger_id` с одинаковым числом секций, чтобы все строки одного леджера в обеих
таблицах лежали в секциях с одним номером. Строка без подходящей секции MUST
NOT существовать: набор секций покрывает все значения `ledger_id`.

#### Scenario: Строки одного леджера в одной секции
- **WHEN** в леджер L через `POST /sync/push` записаны операции и связь
  операций
- **THEN** все операции L лежат в одной секции `operation`, а связи L — в
  секции `operation_link` с тем же номером

#### Scenario: Любой новый леджер принимается
- **WHEN** создаётся новый леджер с произвольным `ledger_id` и в него
  пишется первая операция
- **THEN** запись проходит без ошибки «нет секции для строки»

### Requirement: Запрос одного леджера читает одну секцию
Запросы, в которых `ledger_id` задан значением или параметром (pull,
лента, отчёты, балансы), MUST читать только секцию этого леджера в каждой из
двух таблиц.

#### Scenario: Pull по курсору
- **WHEN** выполняется выборка изменений `operation` для леджера L с
  `seq > курсор`, как её делает `GET /sync/pull`
- **THEN** план запроса (`EXPLAIN`) обращается к одной секции `operation`

#### Scenario: Функция отчёта за период
- **WHEN** вызывается функция отчёта (например,
  `f_balance_to_date(ledger, date, currency)`) для леджера L
- **THEN** при выполнении читается только секция L, остальные секции
  отсекаются

### Requirement: Контракт таблиц для кода не меняется
Смена физического хранения MUST NOT менять имена таблиц, состав и типы
столбцов, первичные ключи `(ledger_id, uuid)`, ограничения целостности и
поведение триггеров `updated_at`. Код wallet-api и wallet-report и клиенты
синка MUST работать без правок.

#### Scenario: Синк без изменений протокола
- **WHEN** android-wallet выполняет `POST /sync/push` и `GET /sync/pull`
  после миграции
- **THEN** ответы совпадают по форме и содержанию с ответами до миграции
  (контракт — `openapi.yaml`)

#### Scenario: Повторный push той же операции
- **WHEN** push присылает операцию с уже существующим `(ledger_id, uuid)`
- **THEN** строка обновляется (или конфликтует по `base_seq`) так же, как до
  секционирования, дубль не появляется

#### Scenario: Чужой счёт в операции
- **WHEN** push присылает операцию леджера L со счётом из другого леджера
- **THEN** запись отклоняется внешним ключом на `account`, как и раньше

### Requirement: Каскадное удаление сохраняется
Удаление леджера MUST удалять его операции и связи. Физическое удаление
операции MUST удалять связи, которые на неё ссылаются.

#### Scenario: Удаление леджера
- **WHEN** леджер L удаляется (удаление аккаунта пользователя)
- **THEN** в `operation` и `operation_link` не остаётся строк L

#### Scenario: Физическое удаление операции
- **WHEN** строка `operation` удаляется физически (`DELETE`)
- **THEN** строки `operation_link`, где она `main_uuid` или `link_uuid`,
  удаляются вместе с ней

### Requirement: Права ролей на секционированные таблицы
Роль `wallet_api` MUST иметь DML (`SELECT`, `INSERT`, `UPDATE`, `DELETE`), а
`wallet_reader` — `SELECT` на `operation` и `operation_link` и на вьюхи над
ними. Ни одна app-роль MUST NOT получать DDL.

#### Scenario: Отчёты wallet-report после миграции
- **WHEN** wallet-report под `wallet_reader` запрашивает отчёт по
  операциям
- **THEN** запрос выполняется без `permission denied`

#### Scenario: DDL под app-ролью
- **WHEN** под ролью `wallet_api` выполняется `CREATE TABLE ... PARTITION OF
  operation`
- **THEN** команда отклоняется с ошибкой прав

### Requirement: Смена хранения обратима и сохраняет данные
Миграция хранения MUST переносить все строки без потерь и изменений и MUST
иметь down-миграцию, возвращающую прежнее устройство с теми же данными.

#### Scenario: Данные после up
- **WHEN** миграция up применяется к базе с данными
- **THEN** число строк и контрольная сумма содержимого `operation` и
  `operation_link` совпадают с исходными, текущий `seq` каждого леджера не
  меняется

#### Scenario: Откат
- **WHEN** после up применяется down
- **THEN** таблицы снова обычные (не секционированные), данные совпадают с
  исходными, сервис и отчёты работают
