# Design

## Context

Мотивация — proposal.md, «Why»; продуктовые решения зафиксированы в issue
`.github-private#10` и общие для четырёх парных changes (`wallet-api`,
`android-wallet`, `wallet-report`, `wallet-telegram`).

На что опираемся:

- Любая операция — проводка `acc_fr → acc_to`; перевод «кошелёк → кошелёк»
  не доход и не расход. Отрицательный баланс кошелька — штатный случай.
  Поэтому долг как перевод на кошелёк контрагента не попадает в доходы и
  расходы без правки отчётных функций.
- Расширение кошелька таблицей с общим PK уже есть: `account_asset`
  (`000033`), с каскадом tombstone (`000035`) и порядком применения
  `account_operating → account_asset`. `account_debt` повторяет шаблон.
- Имя счёта уникально без учёта регистра среди живых (`000024`); тот же
  приём подходит для `counterparty`.
- Синк описан таблицей `push_tables()` в `src/sync_repo.cpp`, порядок
  применения — `kApplyOrder`, он же `TABLE_ORDER` в Android `SyncEngine`
  и копия в `wallet-report/src/sync_repo.cpp`.
- Неизвестную таблицу push в полном режиме молча пропускает.

## Goals / Non-Goals

**Goals:**
- Долг хранится обычными проводками; «кто кому сколько должен» выводится из
  баланса долговых кошельков.
- Несколько займов одному человеку — несколько кошельков, без новой
  сущности «заём».
- Старые клиенты видят долговой кошелёк обычным кошельком с верным балансом.

**Non-Goals:**
- Проценты, ставка, график, напоминания: слой поверх тех же кошельков позже.
- Распределение возвратов по займам: пользователь сам выбирает кошелёк.
- Телефонная книга: только телефон, на сервер уходит `name`.
- Запрет «актив и долг одновременно» на сервере.

## Decisions

### D1. `counterparty` — отдельная таблица

`(ledger_id, uuid)` PK, `name text NOT NULL`, `comment text NOT NULL DEFAULT
''`, `icon_uuid uuid NULL`, `is_archived boolean NOT NULL DEFAULT false`,
колонки синка (`seq`, `deleted_at`, `updated_by`, как у `account_asset`),
триггер `set_updated_at`, индекс `(ledger_id, seq)`. Уникальный индекс
`(ledger_id, lower(btrim(name))) WHERE deleted_at IS NULL`. Нарушение
уникальности → `409 duplicate_name` тем же путём, что у `account`.

Решение «отдельная таблица, а не строка в `account_debt`» принято в issue:
у контрагента есть собственные данные (комментарий, иконка, архив), одно
место переименования и группа для нескольких кошельков.

*Альтернатива:* `counterparty_name` в `account_debt`. Отклонено владельцем:
опечатки разводят человека на двоих, нет архива и ограничения удаления.

### D2. `account_debt` — по образцу `account_asset`

`(ledger_id, uuid)` PK и FK на `account_operating (ledger_id, uuid) ON
DELETE CASCADE`; `counterparty_uuid uuid NOT NULL` с составным FK на
`counterparty (ledger_id, uuid)`; `comment text NOT NULL DEFAULT ''`;
`due_date date NULL`; колонки синка. `due_date` и `comment` описывают
конкретный заём (кошелёк).

Уникальности по `(counterparty_uuid, валюта)` нет намеренно: так второй
заём тому же человеку в той же валюте — просто ещё один кошелёк со своим
сроком (ответ владельца на вопрос 3).

### D3. Колонки: что обязательно в push

`counterparty_uuid` обязательна; `comment` обязательна (как у актива);
`due_date` и `counterparty.icon_uuid` — необязательны (отсутствие = `NULL`,
неверный тип = `400 invalid_row`). Нужен механизм необязательных колонок:
он уже введён для `currency.show_in_equivalent`, используем тот же путь в
`TableSpec`.

### D4. Целостность

- **Удаление контрагента.** В `push_batch` строка `counterparty` с
  `deleted = true` проверяется: есть живой `account_debt` с этим
  `counterparty_uuid` → `409 {"error":"counterparty_in_use"}`, батч
  откатывается. Проверка идёт после применения остальных таблиц батча, чтобы
  батч «снять `account_debt` и удалить контрагента» проходил. Порядок
  `counterparty → account_debt` в `kApplyOrder` этому не мешает: проверка —
  отдельный шаг в конце транзакции.
- **Каскад tombstone кошелька.** По образцу `000035`: мягкое удаление
  кошелька гасит `account_debt` (триггер или тот же механизм, что у
  `account_asset`). Контрагента каскад не трогает.
- **Архивация контрагента.** `is_archived` — признак интерфейса, на долги не
  влияет.
- **Удаление леджера.** Таблицы входят в удаление леджера целиком (тест
  `test_account_deletion`).

### D5. Признак долга — в `v_account_operating`

`CREATE OR REPLACE VIEW v_account_operating` с `LEFT JOIN account_debt ad
… AND ad.deleted_at IS NULL` и колонкой `counterparty_uuid` в конце (после
`asset_type`, `include_in_net_worth`). Её получают `f_balance_to_date`,
`f_balance_to_dates`, `f_balance_series` в конце `RETURNS TABLE` →
`DROP FUNCTION` + `CREATE` + `GRANT EXECUTE`. Итог «мне должны / я должен»
считает wallet-report по знаку баланса; отдельной итоговой функции нет.

### D6. `kind = 'debt'` в ленте

В `f_operations_for_period` ветка `'debt'` срабатывает, когда ровно одна из
сторон — долговой кошелёк, а другая — недолговой кошелёк. Перевод между
двумя долговыми и проводки «долговой кошелёк ↔ категория» не меняют вид.
Если влит `add-operations-filter-functions`, фильтр `kind` и функция итога
принимают `'debt'` в той же миграции. Это даёт клиентам подпись «Дал /
Взял / Вернул» без хранения направления в операции (см. D8).

### D7. `f_debts_for_period`

Сигнатура: `(p_ledger_id uuid, p_from timestamp, p_to timestamp,
p_eq_currency uuid)`, `STABLE PARALLEL SAFE`, `SECURITY INVOKER`, `GRANT
EXECUTE` для `wallet_reader`. Строка на каждый живой долговой кошелёк
(живы `account`, `account_operating`, `account_debt`).

| Колонка | Смысл |
| --- | --- |
| `counterparty_uuid`, `counterparty_name`, `counterparty_archived` | контрагент |
| `account_uuid`, `account_name`, `account_archived` | долговой кошелёк |
| `currency_uuid`, `symbol`, `"precision"` | валюта кошелька |
| `due_date`, `comment` | условия займа |
| `balance_from` | баланс строго до `p_from` |
| `inflow`, `outflow` | суммы проводок на/с кошелька за `p_from..p_to` включительно |
| `balance_to` | баланс на `p_to` включительно |
| `balance_to_eq`, `inflow_eq`, `outflow_eq` | то же по одному курсу `<= p_to`; `NULL` без курса |

Один курс на `p_to`, а не по датам проводок — как в `f_assets_for_period`
(`capital-assets` D7): тождество `balance_to = balance_from + inflow −
outflow` сохраняется и в эквиваленте. Прощение и проценты приходят
проводками с категорией, поэтому входят в `inflow`/`outflow` как любое
движение по кошельку.

### D8. Направление и подпись не хранятся на сервере

«Дал» / «Взял» / «Вернул» зависят от баланса *до* проводки, а правка
задним числом его меняет. Сервер отдаёт только `kind = 'debt'` и
направление проводки; подпись вычисляет клиент по накопленному балансу.

### D9. Прощение долга — обычная категория

Прощение — проводка «долговой кошелёк → категория» (расход) или «категория →
долговой кошелёк» (доход), где категорию выбирает пользователь; клиент по
умолчанию предлагает категорию «Списание долгов» и создаёт её как обычную,
не системную. Новое значение `system_kind` не нужно: прощение — реальный
расход и должно попадать в отчёты. CHECK `system_kind` не меняется.

*Альтернатива:* `system_kind = 4`. Отклонено: потребовало бы исключений в
шести отчётных функциях ради того, что должно считаться расходом.

### D10. Импорт Money Lover

`tools/moneylover/csv_export.py` сейчас отображает `Debt`, `Loan` и `Debt
Collection` в `unknown`. Они становятся долговыми кошельками: контрагент —
из поля «with» строки, а если оно пустое — из заметки; направление —
по тому, расход строка или доход в выгрузке. Точное соответствие трёх
категорий направлению проверяется на реальных выгрузках при реализации
(задача 6.1), а не заложено в спеку.

### D11. Номер миграции — следующий свободный

Один файл `0000NN_debts.up.sql` / `.down.sql`. Сейчас последний — `000035`;
`partition-operation-by-ledger` тоже пересоздаёт виды и функции, поэтому
номер и источники определений выбираются при реализации. Down возвращает
прежние определения вида и функций и делает `DROP TABLE account_debt,
counterparty`.

## Совместимость

| Клиент | Что видит после миграции |
| --- | --- |
| Android без поддержки | `counterparty` и `account_debt` в pull игнорирует; долговой кошелёк — обычный кошелёк с верным балансом и входит в ликвидный итог; операции — обычные переводы |
| Android с поддержкой | полное поведение (парный change) |
| wallet-telegram | до парного change долговые кошельки остаются в выборе трат |
| wallet-report старой версии | работает: новые колонки функций в конце, читает по имени |

## Risks / Trade-offs

- [Android с долгами выходит раньше сервера] → push молча пропускает
  неизвестные таблицы, клиент снимает `dirty`, и признак не доедет никогда.
  → Выкат строго: миграция и wallet-api раньше APK; в android-wallet —
  повторная отправка всех `counterparty` и `account_debt` при первом синке
  после обновления.
- [Контрагент удалён на одном устройстве, пока на другом заведён долг] →
  `409 counterparty_in_use` у первого, второе устройство получает
  tombstone контрагента при pull. Клиент должен разрешить это переклейкой
  на выжившего контрагента (парный change).
- [Миграции конфликтуют с `partition-operation-by-ledger`] → кто влит
  позже, берёт текущие определения из последней миграции; первая задача —
  сверка.
- [Пользователь записал возврат не в тот заём] → общий итог по контрагенту
  верен, остатки по займам расходятся; исправляется правкой операции.
- [Кошелёк и актив, и долг] → схема не запрещает; клиент не предлагает.

## Migration Plan

1. Влить миграцию; накатить на test, прогнать интеграционные тесты
   wallet-api и wallet-report.
2. Выкатить wallet-api и wallet-report в prod.
3. Обновить Android, затем бот (убрать долговые кошельки из выбора).
4. Откат: wallet-api и wallet-report — предыдущим тегом; миграция назад —
   только пока нет строк `account_debt` и `counterparty`.

## Open Questions

- Нужно ли серверу отдавать `due_date`-просрочку отдельным флагом или
  достаточно даты (клиент сравнивает с сегодняшней) — на схему не влияет.
