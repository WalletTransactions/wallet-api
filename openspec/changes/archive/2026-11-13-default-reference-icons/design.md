# Design

## Context

Мотивация и состав — в `proposal.md`, требования — в
`specs/default-reference-icons/spec.md`. Что есть сейчас:

- Общая иконка — строка `icon` с `ledger_id IS NULL` плюс `blob` по SHA-256
  (`schema/table/icon.sql`, `blob.sql`). Имя уникально среди живых общих
  (`uq_icon_name_reference`, регистр учитывается). `seq` выдаёт
  `next_seq('00000000-0000-0000-0000-000000000001')`; на батч — один вызов
  (`schema/function/next_seq.sql`, `reference_icons_repo.cpp`).
- Миграции — `golang-migrate`, `migrations/NNNNNN_*.up/down.sql`, последняя
  `000036_debts`; существующие не правятся (правило проекта).
- Набор телефона — `android-wallet/app/src/main/assets/seed.json`: 65
  `category_icons` (Fluent 3D, `res/drawable/fl_*.png`, в том числе `unknown`),
  7 `flag_icons` и флаги 15 валют; всего 87 уникальных имён, из них 22 флага.
  11 флагов на телефоне — векторы Android XML (`flag_albania`, `flag_gbp`,
  `flag_byn`, `flag_uah`, `flag_kazakhstan`, `flag_georgia`, `flag_amd`,
  `flag_aed`, `flag_cny`, `flag_thb`, `flag_try`), PNG для них нет.
- Клиент подбирает серверного заместителя своей иконки по SHA-256 картинки,
  затем по имени без учёта регистра, затем берёт `unknown`
  (`android-wallet/openspec/specs/icon-sync`). Поэтому имена набора
  определяют, найдёт ли телефон заместителей.

## Goals / Non-Goals

**Goals:**
- На любой базе после миграций есть общий набор, совпадающий с набором
  телефона по именам; чистая база годится для веба и синка сразу.
- Миграция безопасна для уже работающих баз (prod): не ломается на иконках
  администратора и не создаёт дублей.

**Non-Goals:**
- Автоматическая синхронизация набора с `seed.json` телефона после этой
  миграции: набор — снимок на момент миграции, дальнейшие изменения идут
  новой миграцией или через экран «Иконки».
- Изменение API, `openapi.yaml`, клиентов синка и `wallet-web`.
- Картинки вне набора (иконки пользователей из галереи).
- Выкат на test (rc-тег) — отдельная задача после слияния.

## Decisions

**1. SQL-миграция с данными внутри, а не загрузка при старте сервиса.**
`up.sql` вставляет байты картинок сам (base64 в `decode(..., 'base64')`).
Альтернативы: подгружать файлы кодом `wallet-api` при старте (выход за
рамки «миграции — единственный владелец схемы и её содержимого»,
`wallet-schema-ownership`, и результат зависел бы от файлов в образе) или
`pg_read_binary_file` (нужны права суперпользователя и файлы на хосте БД).
Base64, а не hex: SQL получается около 2 МБ вместо 3 МБ.

**2. Детерминированный `uuid` от имени.**
`md5('reference-icon:' || lower(name))::uuid` — одна и та же иконка получает
один и тот же `uuid` на любой базе и при любом повторе. Это даёт
идемпотентность (`ON CONFLICT (uuid) DO NOTHING`) и позволяет `down` находить
свои строки, не трогая иконки администратора.

**3. Пропуск иконок, имя которых уже занято.**
Вставка только `WHERE NOT EXISTS` живой общей иконки с тем же именем без
учёта регистра (администратор мог завести `cinema`, набор несёт `Cinema`).
Так на prod не возникает конфликта `uq_icon_name_reference`, а работа
администратора остаётся нетронутой. Удалённые (`deleted_at` задан) не
мешают. Цена: если администратор успел завести иконку с таким же именем, но
другой картинкой, набор в этом месте с телефоном не совпадёт; это допустимо
и описано в спецификации.

**4. Один `seq` на всю вставку.**
В `DO`-блоке `seq` берётся одним вызовом `next_seq(...)` только если есть
что вставлять (повторный накат без изменений поток не двигает), все новые
строки получают его же — как атомарный батч синка. Курсор телефона после
этого проходит набор одной страницей или несколькими без потерь.

**5. `blob` — по хешу базы.**
`sha256(bytes)` считает Postgres, `INSERT ... ON CONFLICT (sha256) DO NOTHING`.
В SQL нет хардкоженных хешей, которые могли бы разойтись с байтами.

**6. Генератор в `scripts/gen_default_icons.py`, PNG — в репозитории.**
Два режима: `collect` (читает `seed.json` и `res/drawable` из
`android-wallet`, копирует `fl_*.png` и растеризует векторные флаги в
`migrations/default_icons/<имя>.png`, пишет `manifest.json` с именем,
`icon_type` и файлом) и `build` (по манифесту и PNG пишет `up.sql` и
`down.sql`). Миграция воспроизводима из репозитория без доступа к
`android-wallet`. Размер каждого PNG проверяется на `blob_bytes_check`
(≤ 1 МиБ). Альтернатива — писать SQL вручную — отвергнута: 87 иконок и
ошибки в имени разорвали бы соответствие телефону.

**7. Растеризация флагов-векторов.**
Флаги на телефоне — простые `vector` (круг-клип `clip-path`, прямоугольники
и пути без градиентов). Генератор переводит `pathData` в SVG и рисует PNG
64×64 (как остальные флаги-PNG), прозрачный фон. Инструмент рендера —
`cairosvg` в виртуальном окружении разработчика (в образе сервиса не нужен,
запускается один раз); запасной путь — `rsvg-convert`/Inkscape. Растеризацию
проверяет глазами владелец при ревью PNG; тест генератора проверяет только
размер, формат и имена.

**8. `down.sql` удаляет по `uuid` набора.**
`DELETE FROM icon WHERE uuid IN (<детерминированные uuid>)`, затем
`DELETE FROM blob` только тех `sha256`, на которые не осталось ссылок
(`NOT EXISTS (SELECT 1 FROM icon ...)` в той же транзакции). Иконки
администратора и их `blob` не задеваются. Откат — как у `000036`: строки
уносит без следа, `seq` назад не возвращается.

**9. `unknown` в наборе.**
`unknown` есть в `category_icons` телефона (`fl_white_question_mark`), так что
запасной заместитель по `icon-sync` появляется вместе с набором.

**10. Другие сервисы.**
`android-wallet`: правок нет, проверяется на устройстве (синк Pixel без
«нет иконки-заместителя», android-wallet#44). `wallet-web`, `wallet-report`,
`wallet-telegram`: правок нет, иконки появляются в уже существующих выдачах.
Поведение без сети не затрагивается: миграция работает внутри БД.

## Risks / Trade-offs

- [Большой файл миграции, около 2,5 МБ SQL] → накатка измерена 2026-11-13 на
  Postgres 16: 0,33–0,43 с вместе с запуском `psql` (87 иконок, 86 blob,
  2,4 МБ), результат одинаков на пустой базе и на базе с данными (таблицы
  иконок малы). Файл не правится руками, только генератором; тест генератора
  падает, если SQL разошёлся.
- [Расхождение с телефоном при будущей смене набора] → набор — снимок
  (Non-Goal); любое изменение набора телефона сопровождается новой миграцией
  и записью в `tasks` change того набора.
- [Тёмные места растеризации флагов] → PNG коммитятся и смотрятся в ревью;
  перегенерация идёт только вручную.
- [Prod-база уже содержит иконки с теми же именами, но другими картинками]
  → набор пропускает их (решение 3); при желании администратор заменяет их
  на экране «Иконки».
- [Миграция применяется и на prod: «откатывать нельзя»] → `down` есть и
  безопасен (решение 8), но на prod его применять не планируется; выкат на
  prod — отдельной задачей после проверки на test.
