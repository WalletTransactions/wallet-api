# Design: базовая спецификация wallet-api

## Context

Мотивация — в `proposal.md`. Спецификации в `specs/` восстановлены по коду на
коммите `8d31ffc` (main, 2026-10-25), вендоренному wallet-common `0.1.0
(d7dc2e14)`, тестам `tests/` и `tests_integration/`, миграциям
`000001`–`000025`, `schema/` и `openapi.yaml`. Сверялись с README,
`schema/README.md`, `.env.example`, `Containerfile`, `wallet-infra/compose.yaml`
и `infra/env/{deploy,migrate}.sh`.

При расхождении документа и кода источником базы считался **код**.
Расхождения вынесены в раздел «Наблюдения» ниже и в спецификации не
исправлены.

В рабочей копии лежат два незаархивированных изменения:
`purge-synced-tombstones` (закоммичен) и `partition-operation-by-ledger` (не
закоммичен). Их поведение в базу не входит: база описывает то, что
работает сейчас.

## Goals / Non-Goals

**Goals:**
- Описать наблюдаемое поведение сервиса так, чтобы каждый сценарий можно
  было проверить тестом, запросом к API или чтением кода.
- Сохранить обоснование ключевых решений, которое сейчас разбросано по
  README, `schema/README.md` и комментариям.
- Дать двум активным изменениям базу, к которой можно писать дельты.

**Non-Goals:**
- Контракты соседей: google-auth (выпуск токенов), wallet-gateway (грубая
  проверка JWT и маршрутизация), wallet-report (смысл отчётных функций),
  клиенты синка (как они применяют pull).
- Подробная схема таблиц и представлений: она в `schema/` и не дублируется.
  В базу вошли только инварианты, на которые опираются API и соседи.
- Исправление наблюдений и любое изменение поведения.
- Запланированное, но не сделанное: подтверждение прочитанного и чистка
  tombstone, секционирование `operation`, несколько леджеров на
  пользователя, ACL на blob, проверка роли `reader` при полном push,
  загрузка курсов из внешних источников.

## Decisions

### D1. Сервис не выпускает токены, а только проверяет их по JWKS
Подпись RS256 проверяется публичным ключом google-auth, общих секретов в
конфигурации нет. Поверх подписи с шага 3 `TODO_telegram_tokens.md`
проверяются `iss`/`aud`/`scope` одной точкой до хендлеров. Токены без
`aud` отклоняются. Отвергнуто: доверять гейтвею — он проверяет только
подпись и `exp`, а прямой доступ к порту сервиса остаётся. Источник:
README «Как проверяется токен», `access.hpp`.

### D2. Ленивое провизионирование вместо регистрации
Пользователь — это `sub` токена. Личный леджер и устройство появляются
при первом синке. Отдельная регистрация потребовала бы ещё одного шага у
всех клиентов и второго источника идентичности. Источник:
`provisioning.hpp`, `TODO_mobile_sync.md` фаза 2 п. 4.

### D3. Один протокол записи для всех клиентов
Телефоны, веб и Telegram-бот пишут через `POST /sync/push`. Бот получает
узкий режим «только новые операции» по scope `expense:write`, а не
отдельный эндпоинт. Так `seq`, проверка ссылок и идемпотентность одни на
всех. Веб-ручки курсов пишут в те же таблицы с тем же `seq`, поэтому для
телефона правка с веба неотличима от правки с другого телефона. Источник:
`sync.cpp`, README «Курсы валют».

### D4. `seq` — счётчик в таблице, один на батч
`next_seq()` инкрементирует строку `change_stream` в транзакции записи.
Порядок `seq` совпадает с порядком коммитов, и читатель по курсору ничего
не пропускает. У `SEQUENCE` номер выдаётся вне транзакции, а время зависит
от часов устройства. Один `seq` на батч делает группу неразрезаемой при
постраничной выдаче. Источник: `schema/README.md` «Версия строки»,
«Курсор и страницы».

### D5. Два потока: справочники и леджер
Общие справочники (`ledger_id IS NULL`) идут одним потоком на базу, данные
леджера — потоком леджера, включая его собственные копии справочников.
Клиент держит два курсора. Источник: `schema/README.md` «Потоков два».

### D6. Идемпотентность только успешного исхода
По `batch_id` сохраняется только успешный ответ. Конфликт пересчитывается
на каждый повтор: это дёшево и детерминированно, а повтор успешного
применения без кеша потратил бы второй `seq`. Источник: README
«Синхронизация».

### D7. Конфликты, понятные клиенту
Дубль имени счёта отдаёт `existing_uuid` для автоматической переклейки,
недостающая ссылка — `table` и `uuid` для досылки, ошибка формата строки —
`400 invalid_row`. Все три лучше `500`, потому что клиент отличает ожидаемый
конфликт от бага сервера. Источник: инциденты 2026-09-09 и 2026-09-13 в
комментариях `sync_repo`.

### D8. Содержимое иконок отдельно от синка, без ACL
Байты иконок загружаются контентно-адресуемо и дедуплицируются между
пользователями, а в синке едет только хеш. Право на конкретный blob не
проверяется: хеш не секрет, и это осознанно отложено (открытый вопрос
`TODO_mobile_sync.md`). Источник: `blob.hpp`.

### D9. Один леджер на пользователя (MVP)
Ни одна ручка не принимает `ledger_id`. Принятие приглашения при своём
леджере отказывает, кроме замены пустого леджера, где `seq` = 0 гарантирует,
что курсоры устройств тоже на нуле. Источник: `TODO_mobile_sync.md` п. 1.3,
9.7.

### D10. Жёсткое удаление каскадом от леджера
`ledger_id` — единица владения, поэтому удаление аккаунта сводится к
`DELETE FROM ledger` для своих леджеров. Внутриледжерные ключи отложены до
`COMMIT` (миграция `000025`). Удаление в google-auth — отдельный вызов в
порядке, который безопасен при обрыве. Источник: `account_deletion_repo.hpp`.

### D11. Сервис — владелец схемы, роль без DDL
Схема накатывается ролью-мигратором из образа той же версии, сервис только
проверяет маркерные таблицы. wallet-report читает ту же базу ролью
`wallet_reader` без права записи (CQRS-lite). Источник: README «Своя БД»,
миграция `000002`.

### D12. `/healthz` не проверяет зависимости
Liveness без похода в Postgres: сбой зависимости не должен перезапускать
сервис при restart-политике compose. Источник: `docs.cpp`.

### D13. Границы и разбиение базы
Capability нарезаны по наблюдаемым контрактам: доступ, провизионирование,
push, pull, blobs, совместный доступ, курсы, удаление, схема, эксплуатация.
Push и pull разделены: активное изменение `purge-synced-tombstones` трогает
pull и устройство, но не push. Хранение данных (`ledger-data-storage`)
оставлено изменению `partition-operation-by-ledger`.

**Правки у клиентов синка и в wallet-report:** не нужны. Изменение не
меняет ни код, ни схему, ни протокол.

## Risks / Trade-offs

- [База отстаёт от кода] Спецификация снята на конкретный коммит → задачи
  сверки в `tasks.md`; дальнейшие изменения поведения идут через changes.
- [Активные изменения написаны без базы] `purge-synced-tombstones` и
  `partition-operation-by-ledger` → после архивации базы их дельты
  перепроверяются (см. tasks, раздел 4): сброс курсора становится MODIFIED
  к `sync-pull`.
- [Гонка первого провизионирования] Два устройства нового пользователя,
  одновременно вызвавшие первый синк, могут создать два леджера. Риск
  принят осознанно (`provisioning.hpp`) → при переходе на несколько
  леджеров решить блокировкой или уникальностью.
- [Без ACL на blob] Аутентифицированный пользователь может скачать любое
  содержимое по известному хешу → хеш не угадать, содержимое — иконки;
  ACL отложен.
- [Вендоренная wallet-common] Обновление копии может изменить проверку
  токена (`jwt_claims`, `jwks`) или логи → сверка `api-access-control` и
  `service-operations` при `scripts/vendor.sh`.

## Покрытие

Юнит-тесты на `8d31ffc` (сборка в `debian:bookworm-slim`, как в CI):
35 тестов, 0 упавших. Интеграционные тесты — в одноразовом
`postgres:16-alpine` на отдельной docker-сети, миграции `000001`–`000025`
из репозитория (`migrate/migrate:v4.18.3`): 52 теста, 0 упавших.
`run_local.sh` для этого не годится, см. Р18.

Интеграционные тесты вызывают репозитории напрямую, HTTP-слой (`*.cpp`
без `_repo`) покрыт только `test_sync.cpp`. Поэтому коды и тела ответов
ручек в основном сверены чтением кода. Сценарии без теста:

- `api-access-control`: 401 `unauthenticated` у ручек вне `/sync/*`, текст
  ошибок в теле, метрика `jwt_claims_total` и лог `jwt_rejected`;
- `ledger-provisioning`: 404 списка участников до первого синка, леджер из
  `POST /api/currency-pairs`, игнор присланного `ledger_id`, сохранение
  имени устройства, роль читателя при pull, `ledger_id` в ответе первого pull;
- `sync-push`: нет `batch_id`, тело не JSON, неизвестная таблица, перевод с
  `operation_link` одним `seq`, мягкое удаление счёта, усечение даты курса
  (только структурный тест `TableSpec`), дубль имени иконки (`duplicate_key`),
  `reader_cannot_write`;
- `sync-pull`: свой и общий курс в разных потоках, пустая страница, батч
  больше `limit`, tombstone в ответе, смена `ledger_id`, нечисловые
  параметры;
- `icon-blobs`: все сценарии ручек `/sync/blobs*`, кроме `409` у push
  иконки без содержимого;
- `ledger-sharing`: все HTTP-коды (404 без леджера, 403 не-владельцу, 400 на
  роль `owner` и `ttl_days`), список участников читателем, отсутствие
  `token` в списке приглашений;
- `currency-pairs-api`: своя пара поверх общей в списке, пустой список без
  леджера, удаление общей пары (`404`), нулевой курс, доставка правки в pull;
- `account-deletion`: порядок с google-auth (вне сервиса);
- `wallet-schema-ownership`: отказ DDL роли сервиса, проверка схемы при
  старте, отказ записи `wallet_reader` (проверялся вручную 2026-09-04, см.
  `schema/README.md`), порядок `seq` при параллельных коммитах (там же);
  у всех 25 `*.up.sql` есть `*.down.sql`;
- `service-operations`: все сценарии — тестов служебных ручек, логов,
  конфигурации и пула нет.

## Migration Plan

Кода и данных изменение не касается. После сверки (`tasks.md`) change
архивируется: спецификации переносятся в `openspec/specs/`, этот документ
остаётся в `openspec/changes/archive/`. Откат — удалить созданные
спецификации.
