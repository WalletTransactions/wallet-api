# Design

## Context

Мотивация — в `proposal.md`. Исходное состояние:

- `currency_conversion` (миграция 000002) — синк-таблица области
  `ReferenceOrLedger`: `from/to_currency_uuid`, `num`, `currency_pair_uuid`,
  `is_reverse`, `CHECK from <> to`, `num >= 0`; клиенты в неё не пишут, данных
  нет. Ссылка на пару — `ON DELETE CASCADE`.
- `v_currency_conversion` разворачивает каждую `currency_pair` в оба
  направления, `v_currency_conversion_rate` добавляет курсы и тождество
  `X→X = 1` на 2000-01-01. Потребители (`balance_series`, `capital_assets`,
  отчёты) делают `WHERE from=… AND to=… AND date <= d AND (ledger_id IS NULL OR
  ledger_id = L) ORDER BY date DESC, (ledger_id IS NULL) LIMIT 1` — ждут строки
  `(from, to, date, rate)` и сами выбирают «последний ≤ даты».
- Протокол синка описывает таблицы списками в `sync_repo.cpp`; wallet-report
  держит копию списка для засева тестов.

## Goals / Non-Goals

**Goals:**
- Составной курс появляется для потребителей как обычные строки вьюхи.
- Маршруты ездят существующим синком и создаются из веба по пути из валют.
- Результат расчёта детерминирован: прямая пара всегда приоритетнее.

**Non-Goals:**
- Автоматический поиск пути по графу пар.
- Альтернативные маршруты между одной парой валют, общие (справочные)
  маршруты, роли.
- Загрузка курсов для составных пар: курс по маршруту только считается.
- Совместимость со старыми клиентами синка.

## Decisions

### 1. Модель: цепочка строк, `num` — номер шага
Маршрут `from → to` = строки `(ledger, from, to, num=1..N)`; шаг называет
`currency_pair_uuid` и `is_reverse` (0 — от базовой валюты пары к котируемой,
1 — наоборот). Начало и конец шага выводятся из пары и `is_reverse`. Цепочка
**валидна**, если `num` идут подряд с 1, начало шага 1 = `from`, конец шага
`i` = началу шага `i+1`, конец последнего = `to`. Невалидная цепочка
игнорируется (курса нет).
Миграция: `ledger_id` → `NOT NULL`; `CHECK (num BETWEEN 1 AND 3)` (вместо
`>= 0`) — верхняя граница ограничивает стоимость вьюхи; ключ уникальности
живых строк — `(ledger_id, from, to, num)`; второй индекс — по
неупорядоченной паре `(ledger_id, LEAST(from,to), GREATEST(from,to), num)`:
любой маршрут содержит `num = 1`, поэтому прямой и обратный дубль сталкиваются
на нём. Миграция проверяет, что таблица пуста.
*Альтернатива:* одна строка на маршрут с `via_currency_uuid` — проще, но
только два шага, и пара не фиксируется явно. Выбрано по решению владельца —
цепочка гибче.
*Область:* в `sync_repo.cpp` `currency_conversion` — `LedgerOnly`.

### 2. `is_reverse` хранится, но проверяется
Колонка выводима из пары и концов шага, но остаётся, чтобы строки синка
были самодостаточны. REST всегда записывает согласованное значение; в push
несогласованное значение не проверяется построчно (нужна соседняя строка),
а делает цепочку невалидной во вьюхе (концы не стыкуются).

> **Обновление по итогам замера (задача 2.6):** решения 3 и 3a ниже описывают
> исходный замысел «всё во вьюхе». Реализовано иначе — функция `rate_on` с
> прямым путём через неизменённую вьюху и `rate_fallback` для маршрута и USD
> (см. «Результат замера»); правила приоритета и независимых дат те же.

### 3. Составной курс — `UNION ALL` в `v_currency_conversion_rate`
CTE `steps`: живые строки маршрутов с парой (живой) и выведенными концами
шага. CTE `chains`: только валидные цепочки (агрегат по `(ledger, from, to)`
с проверкой неразрывности `num` и стыков по `lag`). Кандидаты дат — объединение
дат живых курсов пар шагов. Для каждой даты `d` курс шага — последний
`date <= d` (для `is_reverse` — `1/rate`), курс маршрута — произведение шагов
(агрегат `route_product(numeric)` в миграции; `exp(sum(ln))` отвергнут из-за
потери точности); строки нет, если курс есть не у всех шагов. Обратное
направление `to → from` — `1/произведение` на тех же датах.
`ledger_id` строки — ledger маршрута; курсы пар шагов видимы по обычному
правилу (`ledger_id IS NULL OR = ledger маршрута`).
*Приоритет:* строка выдаётся только при `NOT EXISTS` живого прямого курса
`(from,to)` на любую дату. Правило «на ту же дату» отвергнуто: потребитель
берёт максимальную дату `<= d` среди всех строк, и свежий составной курс
обошёл бы старый прямой.

### 3a. Кросс через USD по умолчанию — третий уровень во вьюхе
Для пар `(A,B)`, у которых нет ни прямого курса, ни структурно валидной явной
цепочки, вьюха выдаёт строки `A→USD→B` (и обратные) из двух прямых шагов
по тому же правилу независимых дат. USD — валюта с `iso_code = 'USD'`,
видимая леджеру (своя перекрывает общую); хаб зашит константой во вьюхе,
настройки нет (ни в леджере, ни в клиентах). Шаги — только прямые курсы
(без рекурсии), поэтому глубина фиксирована: два шага.
*Приоритет:* прямой → явный маршрут → USD, через `NOT EXISTS` по предыдущим
уровням. Структурно валидный явный маршрут без курса блокирует USD
(молчаливая подмена исказила бы намерение пользователя).
*Стоимость:* уровень применим ко всем парам валют леджера (n²), а не только
к заведённым маршрутам — самое дорогое место change; см. Риски и задачу
замера. *Альтернатива:* хаб-настройка леджера (`hub_currency_uuid`) —
отложена: решено «по умолчанию USD», настройка добавится отдельным change.

### 4. REST: путь из валют, шаги подбирает сервер
`POST /api/currency-routes` принимает `currency_uuids` (путь из 3–4 валют,
различные). Для каждой соседней пары сервер ищет видимую леджеру живую пару
в любом порядке валют; при двух вариантах — пара с базовой валютой «слева»
(как у прямой строки вьюхи). Нет пары для шага — `400` с названием шага.
Все шаги и `from`/`to` пишутся одной транзакцией с одним `next_seq()`.
Для `DELETE` — все шаги по `(from, to)` одним `seq`.
*Альтернатива:* клиент присылает пары и направления — перекладывает логику на
веб и Android. Отвергнуто: клиентам удобнее выбирать валюты.

### 5. Удаление пары снимает маршруты
`currency_pairs_repo` при мягком удалении пары в той же группе (тот же `seq`)
помечает удалёнными все шаги маршрутов, использующих эту пару (целиком
маршрут — все его шаги), иначе после пересоздания пары (новый `uuid`) старый
маршрут остался бы навсегда оборванным. Удаление пары на телефоне идёт через
синк и маршрут не трогает: цепочка оборвётся, курса не будет (спека
`currency-route-rates`).

### 6. Синк: те же правила, что у остальных таблиц
`sync_repo.cpp`: колонки без изменений; ссылки — на `currency` (from/to) и
`currency_pair` (шаг) как сейчас; построчные проверки `num` 1…3, `from` ≠ `to`;
порядок применения не меняется (после `currency_pair_rate`, до `account`).
Дубль маршрута — общий `409 duplicate_key`.

## Risks / Trade-offs

- [Рост стоимости резолва курса в `balance_series`/`capital_assets`: ветка
  `UNION ALL` с коррелированными подзапросами на каждый шаг] → `EXPLAIN
  (ANALYZE)` на копии крупного леджера до и после; индекс по
  `currency_pair_rate (currency_pair_uuid, date desc)` нужен и прямым строкам;
  потолок 3 шага. Запасной план — SQL-функция курса или материализация
  составных курсов в таблицу (оба меняют потребителей).
- [Кросс через USD работает для всех пар валют леджера, а не для заведённых
  маршрутов: вьюха растёт квадратично по числу валют с курсом к USD, а
  предикаты `from/to` потребителей могут не проталкиваться внутрь агрегатов]
  → замер `EXPLAIN (ANALYZE)` обязателен до выката; если не проталкиваются —
  переход на SQL-функцию курса `rate_on(ledger, from, to, date)` с
  переписыванием потребителей (отдельная задача, оценка в замере).
- [Недостроенная или разорванная цепочка молча не даёт курса] → принято:
  push по строкам не может проверить цепочку; REST пишет её целиком, поэтому
  с веба разрыв невозможен.
- [Правило «есть прямой курс — маршрута нет» удивит] → принято ради
  детерминизма; UI может подсказать.
- [Курс устаревает по самому старому шагу] → принято, шаги независимы.
- [Миграция падает, если в таблице вдруг есть строки] → ожидаемо; данных нет.

## Migration Plan

1. Миграция `000043_currency_routes` (up; номер 000042 занят поиском операций): guard на пустую таблицу → `ALTER
   TABLE` (NOT NULL, CHECK, индексы) → агрегат `route_product` → `CREATE OR
   REPLACE VIEW v_currency_conversion_rate` (+ пересоздание
   `v_currency_conversion`, если нужно). Down: возврат ограничений и вьюх.
2. Выкат wallet-api → затем wallet-report и wallet-web → затем клиент.
3. Откат: down-миграция; маршруты, заведённые за время жизни, теряются
   (guard в down предупреждает).

## Результат замера (задача 2.6, 2026-11-18)

Стенд: PostgreSQL 16, один леджер, 40 своих валют (USD + 39), 39 пар к USD с
дневными курсами за ~2 года (26 676 курсов), 40 кошельков, 60 000 операций.
Запросы — потребители вьюхи без правок. «До» — клон базы с откатом 000043.

| Запрос | До (старая вьюха) | После (вьюха 000043) |
| --- | --- | --- |
| `f_balance_series(..., 'month', eq)` за 22 месяца | 1 365 мс | не завершился за 10 мин |
| `f_balance_to_date(..., eq)` | 32 мс | не измерен (тот же резолв курса) |
| один резолв курса `from→to` на дату | 0,17 мс | не завершился за 120 с |

**Вывод: вариант «всё во вьюхе» неприемлем.** План показывает, что предикаты
`from/to` проталкиваются в уровни «прямой» и «явный маршрут», но уровень
«кросс через USD» строится по всем парам валют леджера (n² × даты курсов) с
коррелированными подзапросами и вьюха остаётся не вычисляемой за разумное
время. Миграция в таком виде выкатываться не должна. Запасной план из раздела
«Риски» — SQL-функция курса `rate_on(ledger, from, to, date)` с резолвом «по
запросу» (прямой → маршрут → USD только для запрошенной пары) и
переписыванием потребителей (`f_balance_*`, `f_assets_for_period`,
`f_debts_for_period`, `v_operation_eq`) — принят владельцем (см. ниже).

### Принятый вариант: гибрид (2026-11-18)

`v_currency_conversion_rate` остаётся прежней (прямые курсы + тождественный),
а маршрут и кросс через USD считает SQL-функция `rate_on(ledger, from, to,
date)`: прямой курс (подзапрос к вьюхе, `LIMIT 1`) → иначе `rate_fallback`
(plpgsql: явный маршрут → кросс через USD, только для запрошенной пары).
Потребители (`f_balance_to_date`, `f_balance_to_dates`, `f_balance_series`,
`f_debts_for_period`, `f_assets_for_period`, `v_operation_eq`) переведены с
подзапроса к вьюхе на `rate_on` миграцией 000043 (тела функций переписываются
по тексту с проверкой числа замен). Материализованная вьюха отвергнута: кросс
через USD на этом стенде — 1 млн строк и 98 МБ даже в упрощённом виде (рост
n² × даты), а каждая правка курса требовала бы REFRESH (3 с) — эквивалент
либо устаревал, либо запись курса дорожала.

Замер гибрида (тот же стенд, «до» — клон с откатом 000043):

| Запрос | До | Гибрид |
| --- | --- | --- |
| `f_balance_series` по месяцам, эквивалент USD (все прямые) | 1 414 мс | 1 226 мс |
| `f_balance_series` по месяцам, эквивалент C02 (кросс) | 1 365 мс (курс у 2 из 40 кошельков) | 2 896 мс (у всех 40) |
| `f_balance_to_date`, эквивалент C02 | 36 мс (2 из 40) | 98 мс (40 из 40) |
| `v_operation_eq`, 60 000 операций в C02 | 2 055 мс (курс у 3 000) | 38 308 мс (у всех 60 000) |
| одиночный `rate_on` кросс | — | ≈ 3 мс (план), в пакете ≈ 0,6 мс |

Прямые курсы стоят как раньше (даже чуть быстрее); растёт только цена тех
конверсий, которых раньше вообще не было (≈ 0,5–1 мс на кросс-курс).
Известное узкое место — выборка `v_operation_eq` по ВСЕМУ леджеру в валюте без
прямых пар: 60 000 кросс-конверсий ≈ 38 с. Отчёты ходят с периодом и
фильтрами, поэтому на практике строк на порядки меньше; если понадобится —
пакетная `rates_to(ledger, eq)` или кэш хаба внутри `rate_fallback`.
