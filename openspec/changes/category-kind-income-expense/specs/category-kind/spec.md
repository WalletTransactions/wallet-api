# Spec Delta

## Purpose

Вид категории — «расход», «доход» или «оба»: явный признак на строке `account`,
по которому клиенты разделяют статьи расхода и дохода при вводе операции. Здесь
описаны значения, правило для кошельков и системных категорий, синхронизация и
разметка уже существующих категорий.

## ADDED Requirements

### Requirement: Вид категории
Строка `account` SHALL хранить колонку `category_kind` с закрытым набором
значений: `0` — расход, `1` — доход, `2` — оба. Колонка обязательна, по
умолчанию `2`. Для кошелька (`kind` = 1) и системной категории
(`system_kind` ≠ 0) значение SHALL быть `2`: для них вид не задаётся.

#### Scenario: Новая категория дохода
- **WHEN** клиент присылает строку `account` с `kind` = 0, `system_kind` = 0 и `category_kind` = 1
- **THEN** строка сохраняется, при pull она приходит с `category_kind` = 1

#### Scenario: Умолчание на уровне базы
- **WHEN** строка `account` вставляется в базу без `category_kind`
- **THEN** у неё `category_kind` = 2

### Requirement: Вид меняется как обычное поле
Значение `category_kind` SHALL быть изменяемым: клиент может прислать
существующую строку `account` с другим видом, и сервер применяет изменение
по общим правилам синка (новый `seq`, последняя запись побеждает). Изменение
вида SHALL NOT менять операции и проводки категории.

#### Scenario: Смена вида
- **WHEN** категория «Подарки» с `category_kind` = 0 пришла в push с `category_kind` = 2
- **THEN** при следующем pull устройства получают «Подарки» с видом «оба», операции по ней не изменены

### Requirement: Разметка существующих категорий
Миграция, добавляющая `category_kind`, SHALL разметить каждую живую категорию
(`kind` = 0) по живым операциям (`deleted_at IS NULL`) её леджера: только в
`acc_fr_uuid` — `1`, только в `acc_to_uuid` — `0`, на обеих сторонах или ни
на одной — `2`. Системные категории и кошельки получают `2`.

#### Scenario: Только доход
- **WHEN** по категории «Зарплата» есть только операции «Зарплата → кошелёк»
- **THEN** после миграции у неё `category_kind` = 1

#### Scenario: Только расход
- **WHEN** по категории «Продукты» есть только операции «кошелёк → Продукты»
- **THEN** после миграции у неё `category_kind` = 0

#### Scenario: Обе стороны
- **WHEN** по категории «Подарки» есть и операции «кошелёк → Подарки», и «Подарки → кошелёк»
- **THEN** после миграции у неё `category_kind` = 2

#### Scenario: Категория без операций
- **WHEN** у категории нет ни одной живой операции
- **THEN** после миграции у неё `category_kind` = 2

#### Scenario: Удалённые операции не считаются
- **WHEN** единственная операция «Зарплата → кошелёк» удалена (`deleted_at` задан), а живых операций по категории нет
- **THEN** после миграции у «Зарплаты» `category_kind` = 2

#### Scenario: Системная категория
- **WHEN** категория «Перевод» (`system_kind` = 1) участвует только в операциях «кошелёк → Перевод»
- **THEN** после миграции у неё `category_kind` = 2, а не 0

### Requirement: Разметка доходит до устройств
Если миграция изменила `category_kind` хотя бы у одной категории леджера, она
SHALL выдать этому леджеру новый `seq` (`next_seq`) и записать его в изменённые
строки, чтобы разметка дошла до устройств через `/sync/pull`. Строки, у которых
значение осталось умолчанием `2`, `seq` не меняют.

#### Scenario: Разметка доходит до устройств
- **WHEN** миграция изменила `category_kind` хотя бы у одной категории леджера
- **THEN** изменённые строки получили `seq` больше прежней головы потока леджера и приходят в `/sync/pull` с курсором, дочитанным до миграции

#### Scenario: Умолчание не двигает seq
- **WHEN** у категории по итогам разметки остаётся `category_kind` = 2
- **THEN** её `seq` после миграции прежний

### Requirement: Миграция обратима
Миграция SHALL иметь парный `down`-файл, удаляющий колонку `category_kind`
и ограничение на неё. Существующие миграции SHALL NOT правиться.

#### Scenario: Откат
- **WHEN** применён `down`-файл миграции вида категории
- **THEN** колонки `category_kind` в `account` нет, остальные данные `account` не изменены
