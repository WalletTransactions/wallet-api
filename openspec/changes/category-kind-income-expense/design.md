# Design

## Context

Мотивация — в `proposal.md`. Что есть сейчас:

- `account` — единая таблица кошельков и категорий. Явные признаки уже
  хранятся колонками на самой строке: `kind` (0 категория / 1 кошелёк, меняться
  не должен) и `system_kind` (0–3, системные категории). Добавление колонки
  идёт по тому же пути: миграция, `TableSpec::columns` в `src/sync_repo.cpp`,
  `schema/table/account.sql`, `openapi.yaml`.
- Расширения кошельков (`account_asset`, `account_debt`) — отдельные таблицы
  со своим `seq` и `deleted_at`. Для категорий такого расширения нет.
- Нарушение CHECK (`23514`) в push уже превращается в `400 invalid_row`;
  отсутствующая обязательная колонка — тоже `400` (`json::exception` в
  `build_upsert`).
- Предыдущие бэкфиллы (`000012`, `000013`) серверный `seq` не двигали: клиент
  повторял ту же логику у себя. Здесь разметка зависит от операций, которые на
  устройстве и на сервере могут быть разными на момент миграции, поэтому
  сервер должен отдать результат через `seq` (как `000035`).

Правка нужна у клиентов синка: `android-wallet` (push+pull) — отдельный change.
`wallet-telegram` пишет только операции, строк `account` не шлёт. `wallet-report`
читает `account` напрямую и новую колонку пока не использует.

## Goals / Non-Goals

**Goals:**
- Явный вид категории (`0` расход, `1` доход, `2` оба) в схеме и в синке.
- Разметка существующих категорий по истории операций, доставленная на
  устройства через `/sync/pull`.

**Non-Goals:**
- Фильтры по виду в отчётах (`wallet-report`, `wallet-web`) и в резолвере
  `wallet-telegram`.
- Серверное ограничение «вид имеет смысл только у обычных категорий». Сервер
  не проверяет сочетание `kind` / `system_kind` / `category_kind`: это решает
  клиент, как и сегодня для `system_kind`.
- Запрет менять вид у категории с операциями «не того» вида.

## Decisions

**D1. Колонка в `account`, а не таблица-расширение.** `category_kind smallint
NOT NULL DEFAULT 2 CHECK (category_kind IN (0, 1, 2))`.
Альтернатива — таблица `account_category(kind)` по образцу `account_asset`:
дала бы отдельный `seq` и tombstone, но для признака, который есть у каждой
категории и всегда имеет значение, это лишний join в `v_account_*` и лишняя
таблица в синке. Колонка проще, и вид — не «признак, который можно снять»,
а свойство категории.

**D2. Нумерация `0` расход, `1` доход, `2` оба.** Умолчание — `2`: у кошельков и
системных категорий вида нет, и строка, пришедшая без осмысленного вида, не
должна исчезать из пикеров. Новая обычная категория получает `0` на клиенте
(это правило Android, не сервера).

**D3. Значение изменяемо.** В отличие от `kind`, пользователь меняет вид в
карточке категории. Сервер применяет обычный upsert; ограничений на смену нет
(операции остаются как есть, пикер скрывает неподходящее только при выборе).

**D4. Колонка обязательна в push.** `category_kind` добавляется в
`TableSpec::columns` таблицы `account`, без `optional_columns`. Клиент без неё
получает `400 invalid_row` — совместимость со старыми версиями не нужна.
Значение вне `0..2` ловит CHECK (`23514` → `400`, уже работающий путь).

**D5. Разметка в миграции по живым операциям, с `next_seq`.**

```
для каждого леджера:
  для каждой живой категории (kind = 0, system_kind = 0, deleted_at IS NULL):
    как_приход = EXISTS живая operation, где acc_fr_uuid = категория   -- категория -> кошелёк
    как_расход = EXISTS живая operation, где acc_to_uuid = категория   -- кошелёк -> категория
    category_kind = CASE
        WHEN как_приход AND NOT как_расход THEN 1
        WHEN как_расход AND NOT как_приход THEN 0
        ELSE 2 END
  если хоть одна строка отличается от 2 -> l_seq := next_seq(леджер),
      UPDATE ... SET category_kind = ..., seq = l_seq, updated_by = NULL
```

- Строки, у которых итог `2`, не трогаются: колонка уже `2` по умолчанию, `seq`
  не двигается (меньше лишних строк в pull).
- Строки, которые стали `0`/`1`, получают новый `seq`, один на леджер
  (`updated_by = NULL`, как в `000035`): устройство, которое уже дочитало поток,
  получит их при следующем pull.
- Операции с обеими сторонами-кошельками (переводы) в категориях не участвуют:
  условие смотрит только на `acc_fr_uuid` / `acc_to_uuid`, равные uuid
  категории. Операции в `operation` секционированы по `ledger_id` (`000040`),
  поэтому запрос всегда фильтруется по леджеру — иначе пройдёт по всем
  секциям.
- Системные категории и кошельки не размечаются (остаются `2`).

Альтернатива — не двигать `seq` и повторять разметку на клиенте, как в `000013`.
Отвергнута: на устройстве могут быть непосланные операции, и два устройства
получат разный вид у одной категории; единый источник — сервер.

**D6. `down`-файл только удаляет колонку.** Данные `account` остальных колонок
не меняются; `seq` строк после отката не возвращается (поток только растёт).

## Risks / Trade-offs

- [Устройство с непосланными операциями получит разметку, не учитывающую их] →
  вид — подсказка для пикера, пользователь меняет его в карточке; статья при
  правке старой операции остаётся выбранной (правило клиента).
- [Категория с одной стороной в истории помечена «не тем» видом, например
  «Возврат» только как доход] → признак изменяемый, «оба» ставится вручную.
- [Клиент старой версии получает `400` на push] → принято: совместимость со
  старыми клиентами не нужна, Android обновляется вместе с серверным change.
- [Миграция на большой базе читает `operation` по каждому леджеру] → запрос
  идёт по леджеру и по индексам операций на обе стороны; приемлемо для разовой
  миграции, проверяется на тестовой базе.
- [Порядок выкладки] → сервер раньше Android: новый сервер без нового клиента
  отвечает `400` на push счетов от старого приложения, поэтому релиз клиента
  идёт сразу за релизом сервера (rc-теги test, см. `project_test_release_flow`).
  Если окно между релизами недопустимо, колонку в push можно временно сделать
  необязательной — отложенное решение, см. Open Questions.

## Migration Plan

1. `migrations/000041_category_kind.up.sql`: `ALTER TABLE account ADD COLUMN
   category_kind ...`, комментарий к колонке, разметка (D5), одной транзакцией.
2. Парный `000041_category_kind.down.sql`.
3. `schema/table/account.sql` — колонка и обоснование, как у `kind`.
4. `src/sync_repo.cpp`: `"category_kind"` в колонках `account`; `openapi.yaml`:
   `AccountPushRow` и `AccountPullRow`; `README.md` — список CHECK-значений и
   «Старый клиент без колонки».
5. Откат: `000041 down`, откат образа wallet-api.

## Open Questions

- Нужно ли временно принимать `account` без `category_kind` (умолчание `2`),
  пока на телефонах не обновится приложение? По решению владельца
  совместимость не нужна, поэтому по умолчанию — обязательная колонка.
